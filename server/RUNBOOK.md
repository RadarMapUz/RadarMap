## Панель модератора

Наружу не выставлена намеренно: basic auth по открытому HTTP — это пароль
администратора, отданный любому Wi-Fi по дороге. До сертификата — туннель:

```bash
ssh -L 8093:127.0.0.1:8093 root@45.130.148.94
```

Дальше открыть `http://127.0.0.1:8093/` в браузере. После выпуска сертификата
раскомментировать `location /admin/` в `nginx-radarmap.conf` и завести
`/etc/nginx/.radarmap_admin`.

## Публикация (только с машины владельца — ключ подписи здесь)

```bash
bash server/deploy_api.sh              # api.py + admin.py, рестарт, смоук
bash server/deploy_db.sh <версия>      # база камер: подпись → scp → OTA
bash server/publish_config.sh '{…}'    # пульт; --reset вернуть к дефолтам
bash server/publish_overrides.sh <n>   # решения модератора; --dry-run проверить
```

Номер версии базы: приложение качает, только если `version > своей`. Бандл
сейчас **v13** (3698 камер), прод тоже на v13 (опубликовано 23.10.2026). Публиковать новую версию без новых данных значит
заставить всех скачать тот же мегабайт заново.

### Ворота качества дорог: осознанное обновление базы (28.G, 23.10.2026)

`update_roads.sh` сравнивает метрики кандидата (`road_metrics.py`, рамка
Ташкента) с опубликованной сборкой (`roads_metrics_live.json`) и стоит на
ухудшении больше чем в 1,2 раза. Первая публикация после 28.G ухудшит
`dashes_in_junction`: 18,1 → ≈31 м на 1 км пунктира. Это ожидаемо:
- 18 → 27 пришло с углами перекрёстков 18.10: площадь узла по дугам бордюра
  больше;
- 27 → 31 — только знаменатель: линии на лентах, сжатых до полос уже 2,2 м,
  убраны (−240 км пунктира вдали от узлов), а на проспектах без тега lanes
  добавлены по ширине ленты. Абсолютно пунктира в узлах столько же (около
  48 км).

Публиковать с причиной:

    RADARMAP_ALLOW_WORSE="28.G: база dashes_in_junction — узлы 18.10 и знаменатель" …

После публикации метрики кандидата становятся новой базой
(`publish_roads.sh` копирует их в `roads_metrics_live.json`). Ожидаемые
значения — в `server/review/roads_metrics_28g_tashkent.json`.

Новые метрики 28.G не сравниваются, пока их нет в базе: `arrows_*`,
`marking_jumps`, `junction_colour_mismatch`, `bridge_seams`, `zebra_steps`,
`avenues_unmarked`. Исключение — `arrows_angle_max`: у неё потолок 2°,
и он стоит всегда.

29.A добавила меры контура узла — тоже не сравниваются до первой публикации:
`junction_kerbless`, `junction_overlap`, `junction_teeth`, `junction_notches`
(крупные узлы, через которые идут две разные улицы), `kerb_inside_junction`
(бордюр по асфальту узла), `medians_in_junction` (кромка острова
разделительной внутри площади узла) и `medians_through_zebras` (остров
поперёк перехода), `median_shards` (осколки острова у узла). Бордюр, разделительную в узле и через
зебру build_mvt режет по построению — ожидается 0; осколков — единицы (узкие бетонные острова у узла).
Вырезка Ташкента: 4,8 %, 12,3 %, 0,5 %, 5,3 %, 0, 0, 0, 4 (main: 15 %,
34 %, 0,3 %, 4,8 %, 44, 46, 1334, 2). Сборка печатает «контур перекрёстков: по
устьям …, объединением лент …, по узлам …, оболочкой … (доля)» — доля
оболочки в Ташкенте 0,4 % (main 7,9 %).

32C (27.10.2026): площади узла одного цвета внахлёст сливаются
(`JunctionMerger`; перекрёсток с площадью вдоль одной улицы — нет, и не так,
чтобы слитая начала резать линии полос: тогда нахлёст снимается с одного
куска), острые углы срезаются торцом, выемки и зубцы от сетки 1e-5° чистятся
по кольцу, каким оно ляжет в тайл (`settled_ring`), бордюр на полотне своего
подхода не рисуется (`kerb_off_ribbons`), у запасной оболочки есть бордюр,
у разделительной-линии, раздавшейся у узла шире 3,5 м, там полоса. Вырезка
Ташкента, main → ветка: без бордюра 4,8 → 2,6 %, внахлёст 12,3 → 8,6 %,
зубцы 0,48 → 0,16 %, выемки 5,3 → 4,6 %; остальные меры не хуже.

### Пополнение базы камер из реестра МВД

С v13 (23.10.2026) — `append_registry.py`: сопоставление по адресу, профиль
новых по вырезке OSM вокруг них, twin только там, где пару дала новая камера,
отчёты для модерации. Реестр — вывод `update_cameras.build(fetch())`:

```bash
python3 -I server/append_registry.py --base RadarMap/Resources/cameras.json \
    --registry candidate.json --roads ~/RadarMapBuild/roads.geojsonl \
    --report-new server/review/cameras_vN_new_<дата>.csv \
    --report-gone server/review/cameras_gone_<дата>.csv [--apply]
```

Ниже — прежний путь (v12): сопоставление только по расстоянию 200 м.

```bash
python3 server/merge_cameras.py --base RadarMap/Resources/cameras.json \
                                --source свежий_реестр.json          # показать
python3 server/merge_cameras.py … --apply                            # записать
```

Реестр берётся открытым API портала (ключ не нужен):

```
https://data.egov.uz/apiData/MainData/GetByFile?id=62735473d44f5eea297cef3d&fileType=1&tableType=2
```

**Почему не `update_cameras.py`.** Тот собирает кандидата с нуля и раздаёт id
заново по алфавиту, а ещё возвращает только семь полей из тринадцати. Слить его
поверх боевой базы значит одновременно переклеить чужие проезды в истории на
чужие камеры и стереть геометрию снапа у 3463 записей. `merge_cameras.py`
устроен наоборот: истина по id и геометрии — боевая база, реестр только
дописывает в конец то, чего в ней нет, а перед записью проверяет инвариант
«ни один прежний id не сдвинулся».

Порядок после слияния — все три шага обязательны:

1. поднять `AppConfig.bundledDBVersion`: без этого телефон с уже скачанной
   базой прежней версии новых камер не увидит вовсе;
2. `snap_cameras.py` **по всей базе**, а не по срезу из новых — `twin` и поиск
   дублей считаются глобально и на срезе молча соврут. До снапа новые камеры
   помечены `needsReview`, и приложение честно показывает «координата
   приблизительная». Результат принимать **выборочно**:

   ```bash
   python3 server/adopt_snap.py --base RadarMap/Resources/cameras.json \
                                --snapped cameras.snapped.json --from-id <первый новый> --apply
   ```

   Снап пересчитывает профиль ВСЕЙ базе, и это не безобидно: на прогоне
   01.09.2026 из 3475 старых камер 116 сменили ось, 45 из них больше чем на
   30°, шесть ровно на 90° — то есть уехали на поперечную улицу. При
   `cameraAxisMaxAngle` 55° такая камера перестаёт считаться «нашей дорогой» и
   ЗАМОЛКАЕТ. Изменения разнородны: id=2747 уехал с footway на trunk (явное
   исправление), id=3440 — с trunk на living_street (явная поломка). Их надо
   смотреть глазами по `snap_moves.geojson` на geojson.io, и до тех пор старые
   камеры не трогать;
3. `deploy_db.sh <версия>` — подпись ключом владельца.

## Близкие в Telegram — включить

Близкий открывает `t.me/<бот>?start=f_<адрес семейной ссылки>` и подписывается;
бот пишет «🚗 едет домой — будет примерно в 18:40», «⏱ задерживается» / «🕒 будет
раньше» (сдвиг ≥ 3 мин в любую сторону, не чаще раза в 5 мин), «🏠 дома».
Решение и очередь — в `api.py` (хук `/api/eta` → `family_notify.py`), отправка —
отдельный поток бота. Сроки и что хранится — `RETENTION.md` (`family_*`).

1. В `/opt/radarmap/telegram_bot.conf` дописать `username=<имя бота без @>` —
   то же, что у @BotFather. По нему страница близкого строит ссылку на бота;
   без него бот при старте пишет в журнал «в конфиге нет username». `salt` **не
   менять**: от неё хэши подписок, со сменой `/stop` их не найдёт.
2. Выкладка — строго в этом порядке:

   ```bash
   bash server/deploy_api.sh   # api.py + family_notify.py: хук кладёт сообщения в очередь
   bash server/deploy_bot.sh   # бот: /start f_…, /stop, поток доставки; создаёт family.db
   ```

   Пока бот не поднялся, `family.db` нет — `api.py` молча ничего не делает.
3. Проверить: `journalctl -u radarmap-bot -n 20` — нет «база не открылась» и
   «нет username»; `ls -l /opt/radarmap/api/family.db` — файл есть. С телефона:
   отправить близкому ссылку → «Старт» в Telegram → «Готово: сообщим…»;
   поездка домой → «едет домой»; `/stop` → «подписка снята».
4. Меню команд бот выставляет сам при запуске (см. раздел ниже) — в
   @BotFather `/setcommands` больше не нужен.

Журнал — строки «близкие: …», без номеров чатов и имён: «чат закрыт (403) —
подписка снята», «не доставлено за 4 попытки», «за час отправлено N».
Шлёт лишнее — `systemctl stop radarmap-bot` (заодно встанут отметки через
бота): очередь сама устареет за 10 минут, подписки останутся до починки.

## Telegram-бот: что рядом, метан, перевалы, город (23.1–23.7)

Бот отдаёт то же, что видит приложение: геопозиция → «что рядом» (живые
отметки, камеры, перекрытия, метан), `/metan`, трансляция геопозиции с «ещё
стоит?», `/pereval` с подпиской на опасность, `/city` — подтверждённые треноги
и посты города, `/my`, отмена своей отметки 2 минуты. Тексты — ru и uz.
Подписки — `bot.db` (номер чата зашифрован ключом из соли), сроки —
`RETENTION.md` (`bot_*`).

1. В `/opt/radarmap/telegram_bot.conf` по желанию:
   * `app_url=<ссылка App Store>` — без неё `/app` честно говорит «скоро в App Store»;
   * `owner_hash=…` — для `/stats`. Открытого id владельца в конфиге нет —
     только scrypt-хэш с солью бота. На сервере (id — со stdin, в историю
     оболочки не попадёт):

     ```bash
     python3 /opt/radarmap/api/telegram_bot.py --owner-hash   # ввести свой Telegram-id, Enter
     ```

     Строку `owner_hash=…` из вывода дописать в конфиг. То же одной строкой
     (та же функция, `telegram_bot.owner_hash_of`):
     `python3 -c 'import hashlib;s=input("salt: ");i=input("id: ");print("owner_hash="+hashlib.scrypt(f"owner|{i}".encode(),salt=s.encode(),n=4096,r=8,p=1,dklen=32).hex())'`
2. Аватар — в @BotFather → `/setuserpic` (значок приложения `Radar.icon`).
   Имя, описания и меню команд бот выставляет сам при запуске, и только
   если текст изменился (отпечаток — в `bot.db`, таблица `bot_meta`).
3. `bash server/deploy_bot.sh` (после `deploy_api.sh`, если менялся API).
4. Проверить: `journalctl -u radarmap-bot -n 20` — «профиль и меню
   выставлены» (на первом запуске), нет «база камер не читается»; в Telegram:
   `/help`, кнопка «📍 Отправить геопозицию» → карточка «В радиусе 5 км».

Выключить всё, кроме отметок, без выкладки — пульт:
`bash server/publish_config.sh '{"features": {"bot": false}}'` (бот перечитывает
`config.json` раз в 5 минут; подпись проверяет так же, как пульт состояния).

## Когда сломалось

**Не работают маршруты.** Проверить OSRM: `curl -s
'http://127.0.0.1:8090/osrm/route/v1/driving/69.24,41.31;69.28,41.33?overview=false'`.
Не отвечает — `docker ps | grep osrm`, перезапустить контейнер. Пока чинится:

```bash
bash server/publish_config.sh '{"features": {"routing": false}, "message": {"title": "Чиним маршруты", "body": "Оповещения о камерах работают как обычно"}}'
```

Починили — `bash server/publish_config.sh --reset`.

**API отдаёт 500 / «database is locked».** `journalctl -u radarmap-api -n 100`.
Проверить WAL: должно быть `wal`, не `delete`:
`python3 -c "import sqlite3;print(sqlite3.connect('/opt/radarmap/api/reports.db').execute('PRAGMA journal_mode').fetchone())"`.

**Откат кода.** Рядом лежат `api.py.bak.<дата>`: `cp api.py.bak.… api.py &&
systemctl restart radarmap-api`.

**Волна фейковых отметок.** Точечно — в панели, вкладка «Передвижные»,
«Убрать с карты». Массово — `publish_config.sh '{"features":
{"mobileReports": false}}'`, потом разобрать и вернуть.

**Скрыли живую камеру.** Панель → «Камеры» → «Вернуть камеру» →
`publish_overrides.sh <n+1>`. Доедет за 3 часа, на холодном старте сразу.

**Кончилось место.** `du -sh /opt/radarmap/*`. Кандидаты на чистку:
`/opt/radarmap/work` (рабочие файлы снапа), старые `.bak` в `api/`.

## Проверить, что всё живо

Панель → вкладка **«Пульт»** (`/status`). Одна строка на функцию, у
несработавшей — что это значит для водителя. Руками:

```bash
ssh radarmap-vps 'python3 /opt/radarmap/api/status.py; echo $?'   # 0 — нет красного
```

Проверки идут путём телефона (gzip, подпись, sha тайлов), не по диску.
Тревога в Telegram (`notify.py`, токен в `admin.conf`) — только на смену
цвета, поэтому тишина — норма. Пульт «не обновляется» больше 15 минут —
смотреть крон и `/var/log/radarmap-status.log`.
