# План: периоды Итогов — календарь вместо скользящего окна

Составлен 5 августа 2026 по замечанию «фильтр Неделя / Месяц / Всё время
странный». Замечание точное: у нынешнего фильтра три независимых дефекта,
и один из них — прямая ложь пользователю. Ниже разбор и целевая модель.

Смежный план: `plan_itogi_consistency.md` (одна правда на цифру) — его шаг 1
делается первым, он дешёвый и убирает самое заметное расхождение.

---

## Что не так сегодня

### 1. «Всё время» обещает то, чего в данных нет — **критично**

`TripHistory.pruned` при каждом сохранении:
- вырезает **трек** у записей старше 7 дней;
- **удаляет записи целиком** старше 30 дней (кроме последних 7);
- держит максимум 50 записей.

То есть «Всё время» — это фактически «последние 7 поездок плюс всё за
30 дней». Год езды показать невозможно: данных нет. Пожизненная правда живёт
отдельно в `LifetimeStats`, и это единственные честные цифры «за всё время».
Сегмент, который не может выполнить своё название, — худший вид неточности:
пользователь верит числу, а число неполное.

### 2. Скользящее окно вместо календаря

«Неделя» = последние `7 × 86400` секунд от `Date()`. Отсюда:
- цифры меняются **сами по себе**, без единой новой поездки: в 14:00 поездка
  прошлого понедельника ещё в отчёте, в 15:00 уже нет;
- «против прошлого периода» сравнивает два скользящих окна — сравнение
  плавает вместе с часами;
- водитель мыслит календарём («на этой неделе», «в июле»), а получает
  «за последние 168 часов». Совпадает это только по воскресеньям вечером.

### 3. Третий сегмент — это другой экран, а не другой период

При «Всё время»: график по дням исчезает (`chartDays == nil`), дельта
километров, движение рейтинга и вывод «стали ездить чище» не появляются
(сравнивать не с чем), а список молча показывает только 7 последних записей
под заголовком «Последние поездки». Один переключатель меняет не окно, а
состав экрана — это читается как поломка.

### 4. Нет самого частого вопроса — «как я съездил сегодня»

После поездки человек открывает Итоги ради сегодняшнего дня. Сегодня это
закрывается только списком поездок.

## Целевая модель (рекомендация)

### А. Периоды — календарные, с навигацией по времени

Сегменты: **День · Неделя · Месяц**. Под ними — строка периода со стрелками:

```
‹   5–11 августа   ›            (неделя)
‹   вторник, 5 авг ›            (день)
‹   август 2026    ›            (месяц)
```

- Периоды считаются `Calendar` (границы дня/недели/месяца), а не вычитанием
  секунд. Неделя начинается по локали пользователя.
- Стрелки листают назад/вперёд; вперёд из текущего периода — заблокировано.
- Сравнение «с предыдущим» становится честным и понятным: прошлая
  календарная неделя, прошлый месяц.
- Это язык Health, Fitness и банковских приложений — водителю его объяснять
  не нужно.

### Б. «Всё время» уходит из фильтра — но не из приложения

«Всё время» — не период анализа, а другой класс данных. Ему уже есть место:
блок **«За всё время»** внизу экрана (пожизненные счётчики и достижения).
Туда же переезжает вход **«Все поездки»** — отдельный экран со списком всей
сохранённой истории, сгруппированной по месяцам. Так исчезает сегмент,
который врал, и появляется честная формулировка: пожизненные цифры — из
`LifetimeStats`, список — из того, что реально хранится.

### В. Дневные агрегаты (rollup) — фундамент, без которого месяц врёт

Сейчас месячные цифры считаются по полным записям, а записи чистятся.
Значит «Месяц» точен только пока не сработала чистка. Решение — стандартное
для аналитики: **при финише поездки писать компактную дневную запись**
(`TripDay`: дата, км, время в движении, проезды, штрафуемые превышения,
риск в сумах, взвешенный балл, превышения по часам). Она весит десятки байт
и хранится **навсегда**.

Что это даёт:
- «Месяц» и будущий «Год» считаются по rollup'ам — честно и мгновенно,
  независимо от чистки треков;
- политика хранения становится осознанной и объяснимой:
  **треки — 7 дней · полные записи — 30 дней / 50 шт · дневные агрегаты и
  пожизненные счётчики — навсегда**;
- бюджеты производительности (`PerformanceBudgetTests`) остаются зелёными
  на любом горизонте: год — это 365 маленьких строк, а не тысячи записей;
- открывается график «по неделям» для месяца и «по месяцам» для года.

Миграция: бэкфилл rollup'ов из существующей истории при первом запуске —
ровно так же, как уже сделано для `LifetimeStats.rebuilt(from:)`.

### Г. Что показывать, когда данных мало

Правило вместо пустого экрана: если в выбранном календарном периоде поездок
нет — показываем не «пусто», а ближайший период с данными одной кнопкой
(«В июле было 12 поездок — показать»). Сегодняшний `emptyPeriodHint` уже
делает это для «Всё время» — обобщаем.

## Порядок работ

| Шаг | Что | Оценка | Почему в этом порядке |
|-----|-----|--------|----------------------|
| 0 | Консистентность info-шитов (`plan_itogi_consistency.md`, шаги 1–2) | полдня | Самое заметное расхождение, не зависит от остального |
| 1 | `TripDay` + rollup при финише + бэкфилл + тесты | 2 дня | Фундамент: без него календарный месяц так же неточен |
| 2 | Календарные периоды в модели (`StatsPeriod` → `DateInterval` + якорь) и `summary` поверх rollup'ов | 1,5 дня | Чистая логика, покрывается тестами до всякого UI |
| 3 | UI: сегменты Д/Н/М + строка периода со стрелками | 1 день | Опирается на готовую модель |
| 4 | «Все поездки» отдельным экраном, «Всё время» из фильтра убрать | 1 день | Закрывает уход третьего сегмента |
| 5 | Пустой период → ближайший с данными; правило в ARCHITECTURE.md | полдня | Финальная шлифовка |

Итого ~6 рабочих дней. Разбито так, что после каждого шага приложение
рабочее и можно остановиться.

## Чего сознательно не делаем

- **Произвольный диапазон дат** (пикер «с … по …») — за рулём не нужен,
  а сложность добавляет заметную.
- **Год** — включаем только после шага 1, когда rollup'ы накопятся; на
  пустом годе сегмент выглядел бы так же, как сегодняшнее «Всё время».
- **Синхронизацию истории между устройствами** — отдельная тема (iCloud),
  к периодам отношения не имеет.
