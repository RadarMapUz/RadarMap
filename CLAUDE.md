# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RadarMap (Xcode project name; product name "RadarMap", bundle `uz.radarmap.ios`) is a native iOS speed-camera map + voice anti-radar navigator for Uzbekistan. SwiftUI, no third-party dependencies — only Apple frameworks (MapKit, CoreLocation, CoreMotion, AVFoundation, CoreHaptics, ActivityKit, WidgetKit, MetricKit, CarPlay, WatchConnectivity, AppIntents, CryptoKit). It also ships a CarPlay navigator scene and an Apple Watch companion (`RadarWatch`). Paired with a self-hosted VPS backend (camera DB, OSRM routing, speed limits, crowdsourcing API).

**Language convention:** all code comments, user-facing strings, and git commit messages are in Russian. `README.md` is the fullest overview (in Russian). Match this when writing new code, strings, and commits. User-facing text goes through `String(localized:)` and the `Shared/Localizable.xcstrings` catalog (ru + uz); the app also exposes an in-app RU/UZ language override (`AppSettings`).

**`ARCHITECTURE.md`** (Russian) is the companion to this file: it states the layering (MV, no ViewModels) and the 20 coding/review rules the project is written against (errors never swallowed, constants in `AppConfig`, UserDefaults only via `Storage`, network only via `APIClient`, heavy work only via `@concurrent`, silently-applied remote data only via a verified `SignedPayload` and fail-closed, camera alerts never remote-controlled, …). Read it before non-trivial changes.

## Build, test, run

Single-scheme project (`RadarMap`). Four targets: the app (`uz.radarmap.ios`, which also hosts the CarPlay scene), `RadarMapWidgets` (`…ios.widgets` — Live Activity + home widget), `RadarWatch` (`…ios.watchkitapp`, watchOS companion, deploys **watchOS 11.0**), and `RadarMapTests` (`…ios.tests`, XCTest). App + widgets deploy to **iOS 18.0**; the test target and project baseline are iOS 26.2. All four targets sign with `DEVELOPMENT_TEAM = RL7M4Z58CJ` — the paid team. They must stay on one team: the app target used to sit on a personal team, and a personal team can register neither App Groups nor CarPlay, so every device install meant hand-editing the bundle id and emptying entitlements. The app target signs with `RadarMap/RadarMap.entitlements` on device and `RadarMap/RadarMapCarPlay.entitlements` on `iphonesimulator*` only — the simulator does not check the CarPlay entitlement against a profile, so the CarPlay icon appears without Apple's grant (application text: `docs/appstore/carplay-application.md`).

**Use the `mcp__xcode__*` tools for everything Xcode-related — building, tests, previews, build logs, diagnostics, and project-file edits. They are the only supported build/test path for this project — do not use `xcodebuild` or other CLI tools.** They drive the already-open Xcode instance, so they reuse its build state and are far faster on the iterative loop. If Xcode is not running, open the project in Xcode first rather than reaching for a CLI build.

**Every `mcp__xcode__*` tool takes a `tabIdentifier`.** Call `mcp__xcode__XcodeListWindows` once at the start of a session to get it (it also reports the active scheme and run destination), then reuse that identifier for all subsequent calls.

## Architecture

### Dependency injection
`AppEnvironment` (`App/AppEnvironment.swift`) is the composition root — a single `@MainActor @Observable` object, `AppEnvironment.shared`, built once and shared by the phone SwiftUI scene *and* the CarPlay scene (CarPlay may connect before the SwiftUI scene). Injected via SwiftUI `.environment(...)`, read with `@Environment(AppEnvironment.self)`. It owns every service and **wires cross-service callbacks in its `init`** (e.g. `MotionService.onDrivingStart` → start trip; `RouteService.onManeuver` → speak). To understand how a feature is triggered end-to-end, read this `init` first — the services themselves are decoupled and only know about closures.

### Concurrency model
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` + `SWIFT_APPROACHABLE_CONCURRENCY = YES` (Swift 5 language mode). Nearly everything is implicitly `@MainActor`. Because approachable concurrency turns on `NonisolatedNonsendingByDefault`, a plain `nonisolated async` runs on the **caller's** actor — so `Task { await Self.heavy() }` from the main actor stays on main. To actually get off main, heavy work is marked **`@concurrent`** (see `CameraRepository` DB decode, `JSONFile`); stateless utilities (`Log`, `JSONFile`) are `nonisolated enum` so a call from `@concurrent` code doesn't hop back to main. Pure geometry helpers are `nonisolated static`; some still run via `Task.detached` (`RouteService.apply` cameras-along-route, `SpeedLimitService`). `CLLocationManagerDelegate` callbacks are `nonisolated` and hop to `@MainActor` via `Task { @MainActor in ... }`. (See ARCHITECTURE.md rule 11.)

### The heart: `LocationService`
This is the most important and most complex file. It runs **two GPS modes**, selected centrally in `applyLocationMode()`:
- **Silent background** — significant-location-change + up to 20 `CLCircularRegion` geofences (iOS hard limit) around the nearest cameras; the system wakes the app on region entry → local notification. Near-zero battery.
- **Trip mode** (`startTrip`/`endTrip`) — continuous high-accuracy GPS with active alerts even when backgrounded (requires "Always" auth). Auto-started/stopped by `MotionService` (CoreMotion) when `settings.tripStartMode.usesMotion`. `TripStartMode` (`auto`/`smart`/`manual`) replaced the old `autoStartTrip` toggle — `.smart` additionally requires the driver to be recognized (`isDriverRecognized`, from saved places and prior confirmations) and otherwise asks, so a passenger's phone doesn't record a trip.

Behavior the user can steer lives in `AppSettings` as small enums, each with its own title/symbol: `AlertMode` (auto / city / highway — overrides `AlertPolicy`'s detector), `TripStartMode`, `BackgroundAlertMode` (all / radars only / off), `CameraFilter`, `MapAppearance`, `AppLanguage`.

`LocationService` is an orchestrator: nearly all the decision logic lives in **pure, tested `nonisolated` engines** it calls in a fixed order (see the pipeline below). It keeps for itself only what needs the live `CLLocationManager`: adaptive accuracy (relax GPS when far from cameras/maneuvers — `tuneAdaptiveAccuracy`; an open dashboard bumps the cruise tier one step for smooth sketch motion, but **only** while foreground and thermally `.full`), geofence retiling, the stale-fix watchdog, driver/passenger recognition (`confirmDriver`/`markPassenger`), trip stitching on start (`resumePreviousTripIfMerged`), and CoreHaptics escalation via `AlertPlayer.haptic(level:)`. Speed-limit matching and route progress are driven from here (not the UI) so voice keeps working when backgrounded. The speedometer value goes through `SpeedSmoother` (pure, tested): time-based EMA that snaps immediately on a real >6 km/h change — constant weights on the irregular adaptive-GPS tick rate used to drag a braking tail for 5+ seconds.

### The alert pipeline (read this before touching alerts)

Every GPS tick runs through four engines in this order. **The governing rule is asymmetric: silence about a real camera is worse than one extra warning**, so each gate may only mute a camera when it has positive proof the camera is *not* ours; unknown data means warn. Six separate "why was it silent" bugs came out of violating that. The ordering itself now lives in **`Services/LocationGates.swift`** — a pure `nonisolated` module taking a six-field `Situation` plus an externally-supplied "is it on the route" answer — with `LocationGatesTests` pinning the policy (before the extraction the order could only be verified by reading `LocationService` next to a live `CLLocationManager`).

1. **`LocationFilter`** (`Services/`) — the fix-quality gate, ahead of everything. Rejects cached/jumped/inaccurate fixes before they reach alerts, track, or stats (a stale first fix used to register as a real camera pass at a bogus speed, since `PassTracking` takes the zone minimum). It also owns **course trust**: raw `course` only when `courseAccuracy` says so, else course-over-ground from the last two accepted fixes, else `-1` — which switches the directional gates off entirely rather than letting a bad course mute a real camera. Works on a plain `Fix` struct, no `CLLocation`.
2. **Direction / road-shape gates** — `RoadShape` + `RoadGeometry` (`Models/RoadShape.swift`) wrap the per-camera road data shipped in the DB: `dir` (one-way carriageway heading), `axis` (undirected 0–179°, catches driving *over* a camera on a bridge or across an interchange), `cls`/`lanes` (lane half-width instead of one global constant), and `road` (a short polyline of the camera's own carriageway, so "am I on this road" is a real distance to a line, and the axis is taken at the camera's point instead of one axis for a curved road). Muting by direction requires `Camera.allowsDirectionGate` — i.e. `sidesAreProven` (a twin camera facing the other way, or a road known not to be divided). About half the DB cannot prove it, and those cameras may well shoot both sides, so they are never muted this way. `hasTrustedRoadProfile` throws out cameras the snap landed on a footway/crossing/platform (39 in v10) — their "road" says nothing about traffic.
3. **`RoadCorridor`** — the fallback heuristic that replaced the old ±70° cone (at 400 m that cone accepted a camera 375 m sideways, i.e. every parallel street and overpass). It splits the vector to the camera into along-course and lateral components and decides on **lateral offset in metres**: narrow near the car (course is trustworthy, curvature has not accumulated), widening farther out by a small cone so a camera on your own highway past a bend survives. `isAhead` is now just `RoadCorridor.fix(...).along >= -corridorBehindToleranceMeters`. Crowdsourced/sudden points and `needsReview` cameras get the generous highway corridor.
4. **`AlertEngine` → `AlertPolicy`** — `AlertEngine` decides *whether* to fire (escalating levels 1–3 with hysteresis; `effectiveRadius` is the "smart radius" — warn N seconds out, not fixed metres; `isFirst` is tracked separately from `level == 1` because a camera can first be seen late). `AlertPolicy` then decides *how loud*: a city/highway `Detector` (votes from road class, camera density, and an EMA of speed, with a switch cooldown) feeds a three-grade `Style` — `silent` (HUD + one soft tap), `brief` ("Камера, 300 метров" — city, cameras come one after another), `calm` (full phrase with type and side — highway), `urgent` (siren + escalation: sudden points and sustained overspeed at a camera). One uniform shout for every camera is functionally the same as no warning at all, which is what this exists to prevent.

`PassTracking` closes the loop after the fact: it records the minimum speed in an 80 m measurement zone (`passZoneMeters`) at each camera's traverse point, radar-style, feeding «Итоги».

**The record is gated differently from the alert, and that asymmetry is deliberate.** An alert fires on suspicion — one extra beep is cheap. A recorded pass costs a false violation, a wrong hotspot in «Где теряете баллы» and rating points, so it demands proof. Two gates run at the *traverse point*, not at acquisition: the traverse distance (`passTraverseMaxMeters`, 40 m for snapped cameras; 80 m for hand-placed ones whose coordinate never went through the snap), and `PassGeometry.isProvenOffRoad` — the lateral offset from the camera's own carriageway (`road`, present for 99.7% of the DB) against `RoadGeometry.halfWidth`. Checking at the traverse is the whole point: the alert corridor is widest exactly where it is evaluated on approach (68–93 m of lateral tolerance at 400 m), so a camera on the crossing street of an interchange used to slip through acquisition once and then ride all the way into history. `isProvenOffRoad` returns false for "no proof" — on intersections OSM cuts the way into 20–30 m stubs and `lateralOffset` correctly gives nil; that case is caught by the distance gate instead. `TripHistory.sanitized` (`passCleanupMaxMeters`, 70 m — the live gate plus track simplification) is the retro version for history already on disk; it runs once per `Storage.passGeoCleanupN` flag and must repair the daily rollups surgically (`unfolded` old + `folded` new), never by rebuilding `days` from history — that would erase the months whose records are long pruned.

### `RouteService` — routing (own engine)
Apple Maps does not route inside Uzbekistan, so `calculate()` tries `MKDirections` first and falls back to the **self-hosted OSRM server**. Produces engine-agnostic `Variant`s (each with cameras-along-route count and turn-by-turn `RouteStep`s). Live progress (`updateProgress`, called per GPS tick) handles arrival detection, next-camera/next-maneuver, voice maneuver staging, and off-route reroute (with GPS-noise confirmation ticks + cooldown). All the geometry (`project`, `camerasAlong`, `traveledPrefix`) is `nonisolated static` and runs off-main.

### `CameraStore` (`CameraRepository`) — data
Merged set = bundled `Resources/cameras.json` + user-added `custom` + crowdsourced `mobile` − `hiddenIDs`. Two caches invalidated together in `dataChanged()`: a `mergedCache` list and a **grid spatial index** (0.05° ≈ 5.5 km cells) so `nearest(to:)` and `cameras(in:)` never scan all 3475 cameras on the hot path (retile fires every ~1.5 km driven). `revision` increments on any change; UI observes it.

The bundled DB is **v11** (`AppConfig.bundledDBVersion`, 3475 points from data.egov.uz 1-008-0027, snapped to the OSM road axis). A new registry pull is **appended, never rebuilt**: camera ids live in the user's own data (passes in trip history, familiar cameras, hidden ones), so v11 is byte-identical to v10 for its first 3467 records and the 8 new addresses got ids 3496–3503. The profile for a new point is derived by the same `snap_cameras` code, off an OSM extract around it — running the full VPS snap for eight cameras buys nothing and risks moving 3467 that are already right. Beyond the base fields, each camera may carry the road profile the alert pipeline runs on — `axis`, `dir`, `lanes`, `cls`, `bridge`, `road`, `split`, `twin` — all optional, all `nil` on older records, which is why `Camera` exposes the derived guards `sidesAreProven`, `hasTrustedRoadProfile`, and `allowsDirectionGate` instead of letting call sites read the raw flags. `violations` is omitted in the bundled JSON and reconstructed from the type via shared static arrays (one copy in memory for all cameras).

OTA updates (`applyRemote`) verify an **Ed25519 signature** (`Support/OTASignature.swift`, public key in `AppConfig.otaPublicKeyB64`) before anything else — an unsigned or bad-signature payload is never applied (fail closed), which is what makes shipping the DB over plain HTTP acceptable until the HTTPS move. Then it validates, atomically writes `Documents/cameras_remote.json`, and swaps in memory; the downloaded copy survives app updates and is preferred over the bundled DB on next launch. Production and the bundle are both on **v11** (deployed 10.08.2026) — OTA and the build ship the same data. Publishing stays manual: the signing key never leaves the owner's machine, so a DB reaches prod by hand or not at all, and a bundle bumped without a deploy just means the app answers "нет обновлений" — correct, since `RemoteSyncService` applies a payload only when `manifest.version > store.dbVersion`.

### Remote control: three signed files, one verifier

Everything the server can hand the app is applied **without the user's
involvement**, so all of it goes through one `Support/SignedPayload<T>`:
Ed25519 verified *before* the JSON is parsed, and any defect at all — missing
signature, foreign key, malformed JSON, out-of-range value — means falling back
to the build's own values, never the received ones (ARCHITECTURE.md rule 19).

- **`cameras.json` + `version.json`** — the camera DB itself (`RemoteSyncService`).
- **`config.json` — «пульт»** (`RemoteConfig` / `RemoteConfigService`, checked every 6 h).
  Can disable routing, crowdsourced reports and metrics, change the poll
  interval, and show an announcement or an "update required" banner. It
  **cannot touch camera alerts** and never will — the DB is local, the warning
  must work with no server at all, so it must not depend on what a server sends
  (rule 20). The cached pult survives a relaunch (otherwise it is not a kill
  switch) but expires after `remoteConfigMaxAge`, and a fetched-in-the-future
  timestamp is distrusted. Published by `server/publish_config.sh`.
- **`overrides.json`** — the moderator's decisions over the DB
  (`CameraOverride` / `CameraOverrideEngine`, checked every 3 h): `hide`,
  `move`, `retype`, applied to the bundled set only, ahead of `custom`/`mobile`
  in `CameraStore.cameras`. 2 KB instead of a 1 MB DB, so it ships daily and a
  rollback is "publish the file without that line". Three safeguards, because
  hiding a camera produces **silence where a camera stands**: the signature; a
  file hiding more than `overrideMaxHiddenShare` of the base is rejected
  wholesale (protection against a typo in SQL, not against an attacker); and a
  move farther than `overrideMaxMoveMeters` or outside Uzbekistan is dropped
  while the camera stays put. A moved camera loses its whole road profile
  (`axis`, `dir`, `road`, `split`, `twin`) — the snap measured those at a
  *different point*, and `road` is stored as deltas *from* the camera, so it
  would have travelled along. The cost is that the camera warns more often,
  which is the side to err on. Published by `server/publish_overrides.sh`.

### Other services
- `RemoteSyncService` — daily OTA check of the camera DB against the server `version.json` (version + sha + signature), plus the `overrides.json` fetch on its own 3 h cadence.
- `ThermalService` / `PerformanceMode` — reaction to `ProcessInfo.thermalState`. A phone in a windscreen mount under the Tashkent sun reaches `.serious` in 15–20 minutes and iOS cuts the CPU itself; the app used to keep asking for the same work, which is exactly what a user calls "лагает" and what a simulator never shows. `.reduced` cuts the annotation budget to a third, drops heat lines and recomputes the map layer half as often; `.minimal` goes to an eighth and a quarter. What gets cut is a question of priorities, not thrift: behind the wheel voice beats picture, so decorations go first and camera alerts are never touched. The budget never reaches zero — a camera stays a marker or part of a counted cluster, but never vanishes.
- `RoadNetworkService` — road tiles for the dashboard sketch (see `server/build_roads.py` below): a signed index verified on **every** load including from disk, sha256-checked lazy tiles (3×3 neighborhood, fetched only while the dashboard is on screen), memory eviction of far tiles, and `revision` the sketch's `RebuildKey` watches. Any defect → empty source → `FallbackRoadNetwork` falls back to the limit-index network, never to an empty sketch.
- `NetworkMonitor` — one fact (`isOnline`) for one honest sentence. MapKit tiles need the network; the camera DB does not. On the Tashkent–Bukhara road the map goes grey while warnings keep working, and the difference between "приложение сломалось" and "карта не грузится, но я предупреждаю" costs one banner.
- `UsageStatsService` / `UsageStats` — the anonymous daily aggregate (`POST /api/stat`). Counters only: trips, km, alerts, passes, reports, screen opens, plus app/iOS/model and the **location-authorization level** — the single most important number in the product, since without "Always" neither background alerts nor trip auto-start work. No coordinates, no routes, no event timestamps (a test encodes a report and greps it for `lat`/`track`/`timestamp`). Off via a Settings toggle *and* via the pult, on the same 30-day rotating UUID as everything else.
- `MobileCameraService` — crowdsourced mobile-radar reports; polls every 3 min in foreground **and every 75 s for the whole trip, screen off included** (`setTripActive`, wired from `LocationService.onTripStateChanged`) — a tripod stands for an hour, and a report that reaches the driver three minutes late finds them already past it; the pult stays above this, so an interval it deliberately widened is never undercut by a trip. The phone still never tells the server where it is: it takes every live marker (a handful nationwide) and decides for itself what is on its way. **the driver's half of the loop lives here too**: `quickReport` behind `ReportGuard` (one blind tap from the trip bar, the dashboard or CarPlay — refusing a double tap, a same-spot repeat within 3 min / 400 m, and a report from the couch, while letting a report through when standing in traffic *during* a trip), and `MobilePassWatch`, which asks «радар ещё стоял?» exactly once and only after the driver passed within 90 m and left by 180 — silence sends nothing, because «не знаю» corrupts the data worse than absence (the answer is voiced a thank-you and ships with `kind=pass` so moderation can tell a real-pass vote from a couch tap). The prompt waits while a camera alert covers the screen; anonymous device UUID from `Storage.anonymousID`, which **rotates every 30 days** so reports can't be chained into a long-term trace. The server-side trust lifecycle surfaces here too: an unconfirmed report renders as a **ghost marker** (translucent, dashed, «?») and the voice names the source — «Отметка водителей: тренога впереди…» — warn always, but don't sell a rumor as a fact; attribution beats a bare «возможно» because it says where the point came from and makes the community visible, which is how a driver learns their own taps work (`Camera.mobileConfirmed`, nil for the old server keeps the old look). Right after a quick «Радар!» a 6-second `ReportRefineBar` («Что это было?» — тренога/пост/ДТП) lets one tap retype the *same* point via the server's amend; silence honestly leaves «радар».
- `HotspotService` / `TripodHotspots` — **«здесь часто ставят треногу»**. The dislocation schedule for mobile radars is approved daily by the regional traffic-safety chief and is not published — since 2022 a driver cannot even see it at the roadside. But its points repeat, so the reports drivers already send are that schedule rebuilt from below, and nobody else has it. `server/build_hotspots.py` clusters 90 days of radar/tripod reports at 200 m and keeps only what **different people** vouched for (3+ reports, 2+ devices **and** 2+ addresses — one stubborn driver marking the same spot daily must not make the app lie to a city); the payload carries coordinate, counts and a quarter-of-day, never a device, an address or a timestamp, because those reconstruct someone's route. Signed by the owner (`publish_hotspots.sh`), verified through `SignedPayload` on **every** load including from disk, fetched weekly, fail closed to no hints at all.
  The tone rule here is the **inverse** of the camera rule, deliberately: a camera warns on suspicion because silence is worse, but this is a guess about the past, and a guess sold as fact costs trust in the whole app. So no course, no limit, or not speeding all mean silence — while the zone still renders on the map, because showing and saying are different things. `HotspotAlert` (pure, `TripodHotspotsTests`) holds that decision; the voice is one calm line per spot per trip, and the map draws a dashed translucent band, never a camera pin, and only at close zoom.
- `SpeedLimitService` — matches OSM `maxspeed` for the current road (position + course), warns on overspeed with a tolerance; ~3 MB DB, indexed for microsecond per-tick matching.
- `AlertPlayer` — preloaded beep + `AVSpeechSynthesizer` (plays over silent mode, ducks other audio) **plus CoreHaptics**: `haptic(level:)` fires a distinct pattern per alert level instead of one generic buzz.
- `WatchBridgeService` — pushes the trip HUD (speed, next-camera, alert level) to `RadarWatch` over `WatchConnectivity`; the watch escalates with wrist haptics.
- `FeedbackService` — in-app feedback form submission (see `Features/Settings/FeedbackFormView`).
- `CameraDirection` — "smart direction to camera": prefers the route heading, falls back to a smoothed course, with a wide dead zone to avoid flip-flopping.
- `LiveActivityService` / `MetricsService` (MetricKit) / `NotificationService` (one updatable notification per trip, not a stack).
- `App/RadarIntents.swift` — App Intents for Siri / Shortcuts / the Action button; "Начать поездку" runs without opening the app (background launch + "Always" auth is enough to start continuous GPS).

### Configuration
**`Support/AppConfig.swift` is the single source of truth for all tunable constants**, grouped by `// MARK:` sections that mirror the pipeline: alerts/geolocation, the city-highway detector thresholds, GPS fix quality (`LocationFilter`), the camera's road (direction, lanes, road shape), map, pass map, directional alerts, road corridor, trip stitching, OTA, routing, CarPlay. Change behavior here, not scattered across files. Server base is `syncBaseURL` — **`https://soulmed.uz/radarmap`** since 11.08.2026 (OSRM at `/osrm`, API at `/api`, panel at `/admin/`). The move to HTTPS removed `NSAllowsArbitraryLoads` from `Info.plist`. The domain belongs to another project on the same VPS and is wired in by a single `include` line inside its nginx server block, so a rollback is deleting one line; `server/HTTPS.md` documents the whole layout. The old `http://45.130.148.94:8090` stays alive in parallel — a build with the old address may already be in App Store, and switching it off would break it unfixably.

The rest of `Support/` enforces the ARCHITECTURE.md rules and is where the shared plumbing lives, so use it rather than reinventing:
- **`APIClient`** — the only place that touches the network (base URL, per-request/resource timeouts, status check, JSON en/decode, logging). Services describe *what* they want, not *how* to make the request.
- **`Storage`** — typed `UserDefaults` access; every key is a case in one enum, no raw string keys in code. `AppSettings` is the one exception (its own typed `Keys` façade).
- **`Log`** — `os.Logger` split by subsystem (`Log.alerts`, `Log.sync`, …); a `nonisolated enum` so `@concurrent` code can log without hopping to main. Errors are logged, never silently `try?`-swallowed.
- **`Perf`** — `os_signpost` wrappers (DEBUG-only, subsystem `uz.radarmap.ios` / category `perf`) around the hot paths: `handleLocation`, camera-layer build, sketch tick, rating screen, and a `mapBody` *event* counting MapScreen body rebuilds. Profile with Instruments → os_signpost track; release builds compile to nothing.
- **`Wiring`** — `assertSingleAssignment` for the `onX` callback hooks wired in `AppEnvironment.init`. A plain closure property silently loses its first assignment on a second one — that exact bug shipped a dead weekly-digest block — so every hook's `didSet` now traps a re-wire in DEBUG.
- **`JSONFile`** — atomic JSON read/write off-main; **`OTASignature`** — Ed25519 verification of the OTA DB; **`Concurrency`**, **`Formatting`**, **`GeoMath`** — small stateless helpers. `Extensions/SwiftUI/SwiftUIBackports.swift` holds iOS 18 fallbacks for iOS 26 APIs.

### UI
The app follows **MV (Model–View), not MVVM** — there are no ViewModel layers. Views read `@Observable` models/services directly; per-screen UI state lives in an `@Observable` **screen-state model** (e.g. `MapState`, which does buffered annotation loading, long-press "поеду сюда" points, and heading-follow mode), which owns screen state but does not format data for the view. `RootView` gates onboarding → `MapScreen`, and drives foreground/background GPS mode from `scenePhase`. Features are organized by folder under `Features/` (Map, Search, Trip, Settings, Onboarding).

**The main screen learns instead of asking.** The two Дом/Работа circles are gone — empty they read as a chore the app handed the user, while the routine is already on disk. `Models/FrequentPlaces.swift` (pure, `FrequentPlacesTests`) clusters trip endpoints (150 m) and classifies by **routine, not frequency** — home is where you arrive in the evening and leave in the morning, work is where you arrive on a weekday morning; the shop next door is visited more often than work and must never win. Confidence counts *distinct days*, and home is excluded from the work candidates (a morning departure from home and a morning arrival at work look identical). `DestinationSuggestionBar` renders one row — «Домой» / «На работу» — and only when the guess is confident; standing at the place, no guess, or the setting off means no element at all. It deliberately shows no ETA or camera count: that would need a speculative network route nobody asked for, and the tap builds the real one. A manually set address always outranks the learned one. Learned places live on `AppEnvironment.learnedPlaces`, refreshed on scene start and trip end — never in a body.

**Smart silence is visible.** `CameraFamiliarity` has long muted the voice for cameras passed ≥6 times in 30 days with zero overspeeds, but silently — which reads as a broken app. `LocationService.familiarCameraIDs` is now observable and refreshed in `bootstrap()` too, so the map draws those cameras with a green check badge (the `needsReview` «!» badge still outranks it — doubt about position beats calm), the HUD caption says «своя камера — без голоса», and `OneTimeHints.smartSilence` explains it once, gated on the first familiar camera actually existing. Both behaviours are switchable in Settings → «Приложение учится» (`smartSilence`, `destinationSuggestions`); turning one off clears its derived data.

What goes on the map is decided by `CameraMapContent` (pure, tested) **from the data, not the zoom**: if a region holds more cameras than the annotation budget, the whole region is clustered, so no camera is ever silently dropped — it is either a pin or part of a counted cluster. The same file ranks each marker by `CameraTier` — **target / near / background** — because fifty identically-sized dots read as a rash, not a map: the camera 400 m ahead used to look exactly like one 3 km behind. Two rules keep it honest. Demotion is by *distance and route only*, never by direction — a direction mistake costs one extra warning in the alert pipeline but a missed camera on the map. And the reference point is `MapState.focus`, which follows the user only while the map follows them; pan away and it becomes the screen centre, since dimming a district for being far from home is wrong when that district is exactly what you came to look at. `focus` is throttled by `mapFocusStepMeters` — markers read it in their body, so writing it per GPS tick would redraw the whole map every second.

The direction wedge on a marker (`Camera.markerDirection`) is drawn **only where the direction is proven** — the same condition as the alert gate, true for 336 of 3475 cameras in v11. The wedge means "we know the side and may stay silent on it"; drawing it where we cannot stay silent would promise the driver that the oncoming carriageway is safe. Clusters are built off the spatial index with a packed `Int64` key rather than a full scan with string interpolation.

The interface is dark-only ("radar detector" aesthetic), and deliberately set **twice** in `RadarMapApp`: `.preferredColorScheme(.dark)` asks the system for a dark window (status bar), while `.environment(\.colorScheme, .dark)` forces the scheme on our own tree — with only the first, an iOS-level appearance override left glass materials pale and white icons invisible on top of the map. `MapAppearance` (dark/auto/light) is a setting for the **map substrate only** — a dark map glares in daylight. Styled via `DesignSystem/` (`Theme`, `Components`, plus `StatTile`, `SpeedLimitSign`, `ShareCardShell`, `TripMapSnapshot`).

`MapScreen` honors a DEBUG launch argument `-hideCameraAlert`, used to capture clean turn-by-turn screenshots for the CarPlay application.

### Trip domain & «Итоги» (post-trip summary)
Trip analytics live in `Models/`, not in views (ARCHITECTURE.md rule "data in the model"): `TripRecord` (one saved trip, including its `stops: [TripStop]` and the derived moving/stopped split), `TripHistory` (rolling history), `TripStats` (aggregates + track simplification), `DrivingScore` — which also holds `FineSchedule` (Uzbekistan overspeed fines in BRV), `LifetimeStats`, and `Achievement` — plus two newer pure engines:

- **`TripMerge`** — "same trip or a new one?" after a stop. CoreMotion auto-start dies on any sustained stop, so a supermarket run home used to split into three trips and poison the averages. The decision is not one timer: a **manual** trip end is intent and is never overridden, and *where* you stopped matters — an hour at a random place along the way continues the trip, the same twenty minutes at home means you arrived. Paired with `TripStartMode` (`auto`/`smart`/`manual`) in settings and `TripStopsSection` in the UI.
- **`PeriodSummary`** / `StatsPeriod` (week / month / all time) — the period report, including the delta against the previous period. Time is always passed in as a parameter, never read from `Date.now` inside the computation, so it is reproducible in tests.

- **`RatingBreakdown`** — the audit trail of the rating. Because the period rating is a distance-weighted mean, each trip's share of the shortfall is exactly `wᵢ(100 − sᵢ)/Σw`, so the breakdown **sums to `100 − R` and can be checked by addition** (a test does exactly that). On top of that: `sources` re-splits the same shortfall by *camera* (a trip's contribution divided by its own penalty ladder, cap included — «Юнусабад, 4 проезда, −18» is actionable where twelve trip rows are not), `baseline` gives the median and usual range over previous windows, and `ratingIfClean`/`tripScoreIfClean` answer "what if I'd driven that camera at the limit" by the same ladder. All of it is assembled off-main by one `@concurrent screen(...)`.

All the math is `nonisolated static` and unit-tested (`DrivingScoreTests`, `TripMergeTests`, `PeriodSummaryTests`, `PeriodMapTests`, `TripTrackTests`, `RatingBreakdownTests`). `TripDay.swift` also hosts two smaller tested engines: **`RatingTrend`** (weekly rating series from the day rollups — half-open week windows on purpose: `DateInterval.contains` includes the end, and a Monday trip would count in two weeks) and **`MonthGrid`** (calendar layout for the month view), plus `TripHistory.pendingFineNudge` (stale pending fines older than `finePendingNudgeDays`, with the oldest date so the nudge opens the right period). The «Итоги» screens under `Features/Trip/` (`TripStatsSheet`, `TripStatsCards`, `TripDetailSheet`, `TripHistorySection`, `TripStopsSection`, `SpeedProfileChart`, `PassMapSheet`, `PeriodMapSheet`, `PeriodShareCard`, `StatsInfoSheets`, `AllTripsSheet`, `FinesSheet`, `MonthCalendarCard` — the month-as-cells card, tap opens that day, and `TripEndCard` — the «Поездка сохранена» overlay MapScreen shows right after a foreground trip end, with inline merge suggestion) render a driving rating, real fines-based savings ("штрафы за 30 дней"), streaks, per-camera pass speeds, an overspeed-frequency map, and shareable cards. `ReviewPromptModifier` drives the App Store review prompt.

**Sharing** is three cards on one shell (`DesignSystem/ShareCardShell.swift`): `TripShareCard`, `PeriodShareCard`, `AchievementShareCard`, each rendered in two formats — `ShareFormat.feed` (4:5) and `.story` (9:16). `SharePreviewSheet` is the only entry: it shows the card, lets you switch format, and only then hands it to the system share sheet — the old path rendered and shared blind. Entry points: Итоги toolbar, trip detail, `TripEndCard` right after a trip, and an earned achievement (unearned ones can't be shared — a progress bar sent outward reads as a complaint). Two rules that came from real defects: the score colour comes from `Theme.score` alone (the trip card used to paint 55 amber while the app painted it red, so the shared image flattered the driver), and map images go through `ShareMapFrame` — `Image.aspectRatio(.fill) + clipShape` does *not* clip, the 1032 pt-wide snapshot pushed the header or footer off the card until the container started defining the size.

**The rating drill-down** (`RatingDetailSheet`) is one `NavigationStack` four levels deep — период → все вклады → поездка → проезд камеры — and that shape is deliberate: it replaced a sheet that `dismiss()`ed itself to open *another* sheet, so "Назад" landed on Итоги instead of the breakdown you came from. Two views therefore exist in content/wrapper pairs — `TripDetailContent` inside `TripDetailSheet`, `PassDetailView` inside `PassMapSheet` — the wrapper keeps the old sheet entry points, the content is what the stack pushes. Add new entry points against the *content* views.

### CarPlay & Apple Watch
`CarPlay/` (`CarPlaySceneDelegate`, `CarPlayMapScreen`, `CarPlayMapView`) is a full navigator scene — camera map, speed HUD, alerts, quick "where to" routing. The phone scene and CarPlay share one composition root via `AppEnvironment.shared` (CarPlay can connect before the SwiftUI scene comes up). `RadarWatch/` (`RadarWatchApp`, `WatchHUDView`, `WatchSession`) is a watchOS companion showing the trip HUD with escalating wrist haptics, fed by `WatchBridgeService` over `WatchConnectivity`.

**Gotcha:** the CarPlay scene is wired by the hand-written `UIApplicationSceneManifest` in `RadarMap/Info.plist` (role `CPTemplateApplicationSceneSessionRoleApplication` → `$(PRODUCT_MODULE_NAME).CarPlaySceneDelegate`). The app target must therefore **not** set `INFOPLIST_KEY_UIApplicationSceneManifest_Generation` (Xcode's "Generate Info.plist scene manifest" checkbox): it replaces the whole key at build time, leaving `UISceneConfigurations` an empty dict, and CarPlay then crashes on connect with `NSGenericException` «Application does not implement CarPlay template application lifecycle methods in its scene delegate» — the delegate is never instantiated. Verify with `plutil -extract UIApplicationSceneManifest xml1 -o - <built>/RadarMap.app/Info.plist`. `CarPlaySceneDelegate` deliberately implements the `toWindow:`/`fromWindow:` variants of the connect/disconnect callbacks — those are the ones for navigation apps, not deprecated leftovers.

### Widgets & sharing
`RadarMapWidgets` (Live Activity in Dynamic Island + home widgets). The stats widget's hero is **kilometres**, not the rating: people look at a home screen for the fact, and go to «Итоги» for the verdict. The ring fills toward the driver's **own usual week** (median of the previous eight, `WidgetWeek.median` — a median so one trip to Samarkand doesn't make every later week look like a failure); overshoot is said in words, because a second lap reads as a rendering bug. Seven day bars carry the week's shape, `systemLarge` adds month/lifetime/wheel-time tiles and the week's worst place.
  It renders **four states**, and that is the part that was missing: `noAccess` (App Group not granted by the signature — a personal team can't give it, and «you didn't drive» is the wrong thing to say then), `empty` (no trips — an invitation, never a zero), `few` (1 active day or no norm yet: no ring, no bars, no averages, because there is nothing to compare with — the subtitle names the last trip instead), and `full`. `WidgetWeek` (in `Shared/`, tested by `WidgetSnapshotTests`) holds every one of those decisions plus «is this snapshot even about the current week» — the widget writes nothing and computes nothing, the app fills the snapshot on scene-background and every trip end. DEBUG hook `-widgetState empty|few|full` seeds a state so all of them can be screenshotted without waiting for Monday. Shared code lives in `Shared/`: `CameraActivityAttributes` (Live Activity contract) and `SharedDefaults` (App-Group `UserDefaults` snapshot for the home widget; written by `AppEnvironment.refreshWidgetSnapshot()` on scene-background **and** on every trip end — a background auto-stop must not leave the widget stale; the widget itself never computes or refreshes anything). `group.uz.radarmap.ios` is declared in **all three** entitlements files — app-on-device, app-on-simulator, widget — and matches `SharedDefaults.appGroup`. Keep it that way: with the group missing from any one of them `UserDefaults(suiteName:)` silently returns `nil` and the widget renders a placeholder that looks like a widget bug rather than a signing one. The simulator file carries it on purpose, so the widget can be verified before a device install (`xcrun simctl get_app_container <udid> uz.radarmap.ios group.uz.radarmap.ios` shows the container and the written snapshot). The Live Activity is unaffected either way — it goes through ActivityKit, not the App Group.

## Backend

The VPS itself is provisioned separately (nginx, Docker, cron), but the app-facing backend code now lives in **`server/`** — all Python is stdlib-only:
- `api.py` — the crowdsourcing/metrics/feedback/usage API: `sqlite3` + `http.server`, listens on `127.0.0.1:8091`, exposed by nginx at `:8090/api/`. Mobile-radar reports merge via up/down **votes** (`/api/report`, `/api/vote`) with per-device caps against ID rotation; markers are rate-limited and live a **trust lifecycle**: a new report gets a short probation TTL (radar 75 min) and the full one (3/6 h) only after confirmation by an *independent* driver — different device AND different IP — so a planted fake dies on its own while UUID rotation can't self-extend it; `confirmed` ships in `/api/mobile`, a dislike from a fresh IP cuts 30 min off (full hide still needs the 3-distinct-IP quorum), a same-device different-type re-report within 400 m / 10 min is an **amend** (retype own point, not a second marker), and one IP can hold at most 12 live markers. Schema, migrations and indexes live in `init_db()` and run **once at startup** — they used to run on every HTTP request (six `CREATE TABLE IF NOT EXISTS` and four `ALTER TABLE`, all four always throwing). WAL + `busy_timeout` are mandatory: without them one `POST` during a poll handed readers `database is locked` as an instant 500. `BoundedHTTPServer` caps concurrent handlers at 64 and answers 503 above that. `test_api.py` covers it (38 cases). Deployed with `deploy_api.sh` (which also ships `admin.py`); `backup_db.sh` takes a daily consistent `reports.db` snapshot via sqlite's `.backup` (not `cp` — the DB is live) and keeps 7; `healthcheck.sh` (cron, every 5 min) watches api/OSRM/`version.json`/disk/backup freshness and reports **only on a state change** — a message every five minutes stops being read by day two.
- `admin.py` + `admin_auth.py` — the moderation panel: a separate stdlib process on `127.0.0.1:8093`, server-rendered HTML. **Login is a password** (scrypt hash in `/opt/radarmap/admin.conf`, in-memory session cookie, per-IP attempt throttling, `admin.py --set-password`), and `require_secure()` refuses to serve the panel over plain HTTP from anywhere but localhost — a password over plain HTTP is the admin password handed to every Wi-Fi on the way, so until the domain + certbot land it stays on an SSH tunnel. Seven screens: today's attention list, the camera-report queue, live mobile markers, feedback with statuses, health; plus «Люди» — the product funnel from `usage_stats` — and **«Положение»**, the camera-position workflow: a ranked queue of suspicious points (a driver's `wrong_location` complaint outweighs any heuristic; then snap-landed-on-footway, then no road shape at all) leading to `/cameras/<id>/map`, where the camera is dragged on a Yandex satellite map inside a 500 m circle — the same `overrideMaxMoveMeters` the app enforces, so the panel refuses what the phones would reject anyway. The page states the cost of a move on screen: a moved camera loses its measured road profile and starts warning both ways. It is the only page with a script (`static/map.js`, served from a whitelist — never by name from the URL) and the only one with a relaxed CSP, scoped to Yandex's domains. The Yandex key lives in `admin.conf`, never in git. It closes the loop that used to be open: nothing ever wrote `camera_reports.resolved`, and moderation meant a `SELECT` in an ssh session. It **publishes nothing itself** — decisions accumulate in the `overrides` table and the owner signs and ships them with `publish_overrides.sh`, so a compromised VPS can neither hide a camera nor plant one. Hiding is suggested (never applied) at ≥3 `gone` reports from **distinct IPs**, no `still_here` for 14 days, and the oldest report at least a week old; a human confirms with a second click. `test_admin.py` covers it (20 cases), mostly asserting what the panel must *not* do. `radarmap-admin.service` is its systemd unit.
- `snap_cameras.py` / `snap_cameras.sh` — the offline pass that snaps camera coordinates to the OSM road axis **by matching road name** (not just nearest road, to avoid moving a camera onto a parallel street) and derives the per-camera road profile the alert pipeline uses (`axis`, `dir`, `lanes`, `cls`, `bridge`, `road`, `split`, `twin`). It never touches the live DB: outputs land next to it in `server/snap/` (`snap_report.csv`, `snap_moves.geojson`, `snap_dups.csv`) for visual review on geojson.io before you promote them.
- `resnap_moved.py` / `test_resnap_moved.py` — пересъёмка дорожного профиля камер, перенесённых модератором: берёт move-строки из `overrides.json`, выводит профиль заново у новой точки тем же кодом снапа (точку модератора не двигает), переразмечает twin по всей базе; выход — кандидат базы + CSV, дальше обычный `deploy_db.sh` и публикация overrides без влитых move-строк.
- `update_cameras.py` — pulls MVD open-data set 1-008-0027 from data.egov.uz, dedups/normalizes, refuses to proceed on an implausibly small parse, and writes **`cameras_candidate.json`** when the sha changed (idempotent, safe on a schedule). It deliberately does *not* touch the live `cameras.json`/`version.json`: the signing key is not on the VPS, so a compromised server cannot publish cameras. It also watches the MVD accident dataset and shouts into the log if it ever stops being empty. (Its module docstring still describes the older behavior of writing the live file — the code is the authority.)
- `build_roads.py` / `publish_roads.sh` / `test_build_roads.py` — road tiles for the dashboard sketch: the OSM geojsonl extract → 210 tiles of 0.5° (`{"version":1,"roads":[[cls, flags, [lat,lon,dlat,dlon,…]]]}` — delta-coded 1e-5°, flags 1=oneway 2=bridge 4=tunnel) plus `index_payload.json` carrying each tile's sha256. `publish_roads.sh` builds on the VPS, signs the **index** locally with the owner's Ed25519 key, ships tiles first and the signed `roads_index.json` last — one signature covers the whole set, and a tile swapped on the server fails its sha on the phone. Client side: `RoadTiles` (format contract, tested against the same numbers as `test_build_roads.py`), `TileRoadNetwork` (0.01° grid, border duplicates collapsed), `RoadNetworkService` (weekly index, lazy 3×3 coverage driven by dashboard ticks, fail closed), `FallbackRoadNetwork` (tiles where covered, limit-index network otherwise).
- `build_hotspots.py` / `publish_hotspots.sh` / `test_build_hotspots.py` — the tripod memory above: aggregation runs on the VPS (the report DB lives there), signing happens on the owner's machine, so a compromised server can neither invent a hotspot nor erase a real one. `publish_hotspots.sh` re-runs the logic self-test, then validates the payload **before** signing — bounds, thresholds, and a grep for `device`/`ip`/`created`, since a signed leak would already be everywhere by the time anyone noticed.
- `sign_db.sh` / `deploy_db.sh` — the OTA release path, run **by the owner from a local machine**: sign the DB with the Ed25519 key (which lives only at `~/.radarmap/ota_signing.pem`, outside the repo — back it up), build `version.json` (version, count, sha256, sig), then `scp` DB + manifest to the webroot. `deploy_db.sh <version>` is the whole publish step, and it ships `RadarMap/Resources/cameras.json` — i.e. the app bundle and prod are published from the same file.
- `nginx-radarmap.conf` (`:8090` → `/api/`, `/osrm/`, static) and `HTTPS.md` (the domain + certbot migration plan).

The VPS also serves the camera DB and speed-limit files (nginx :8090) and runs OSRM in Docker (CH algorithm, `--mmap`) on an Uzbekistan OSM graph. Since the DB must be signed, refreshing it is no longer fully automatic: per `docs/plan_modules.md` the camera cron is off on purpose and the intended regimen is manual and roughly monthly — run `update_cameras.py` → diff the candidate → `deploy_db.sh <version>` → verify the app picks it up. The road graph + speed limits still refresh monthly.
