Написан 27.09.2026 по живому осмотру (`ssh radarmap-vps`, только чтение) и
проверке каждого файла так, как его забирает телефон (с `Accept-Encoding: gzip`,
как шлёт URLSession).

Главный вывод осмотра — не какая-то одна поломка, а их **класс**: функции
умирают молча. Лимиты месяц отдаются июльские, дороги месяц не собираются,
горячие точки не опубликованы ни разу, решения модератора не выложены — и
ничто из этого не покраснело. Всё приложение построено на правиле «при сбое
сервера — fail closed к своему», и оно работает: водитель не видит ошибки. Но
ровно поэтому их не видит и владелец. План — про то, чтобы каждая функция
имела **сигнал «жива / устарела / мертва»**, видный с одного экрана.

## 1. Правила, по которым строим

1. **Каждая функция = проверка + порог свежести + что это значит для водителя.**
   Нет проверки — функции нет, даже если код есть. Добавил функцию — добавил
   строку на пульт в том же коммите.
2. **Проверяем так, как забирает телефон.** Не «файл лежит на диске», а «GET с
   gzip → подпись сходится → sha совпадает с индексом → дата моложе порога».
   Июльские лимиты прошли бы любую проверку «файл существует».
3. **Репо — единственная правда.** Ничего не правится на сервере руками;
   перед выкатом сверка md5 сервер ↔ репо (`drift.sh`). Сегодня разошлось 7
   файлов, и все — сервер старее.
4. **Подпись только на маке владельца** — как сейчас. Сервер собирает
   кандидатов, мак подписывает и выкладывает. Это не меняем: взломанный VPS не
   должен уметь ни спрятать камеру, ни подсунуть дорогу.
5. **Автоматика собирает, человек публикует, пульт напоминает.** Застрявший
   кандидат (overrides, дороги, горячие точки) — жёлтый через N дней.
6. **Тревога — только на смену состояния** (как уже сделано в сторожe), в
   Telegram через существующий `notify.py`.

## 4. Пульт состояния — «всё ли работает»

### 4.1. Что это

Страница **`/status`** в панели модератора (тот же стиль, тот же вход), плюс
открытый без входа `status.json` для внешнего мониторинга. Одна строка на
функцию:

```
● База камер         v12 · 3511 · 26 дн.        подпись ✓  sha ✓   ▁▁▁▁▁▁▁ 100%
● Лимиты скорости    15.07 (73 дн.)  ← gz≠json  подпись —   sha ✗   ▇▇▇▇▇▇▇  0%
● Дороги/своя карта  09.09 (18 дн.) · кандидат упал 27.09 md5     ▁▁▁▁▇▇▇
● Решения модератора 3 ждут, старшее 12 дн.
● Горячие точки      не опубликованы (404)
● Маршруты           52 мс · граф 15.07 (74 дн.)
● API отметок        ok 41 мс · меток сейчас 0 · за сутки 0
● Бэкап              сегодня 03:17 · копия вне VPS: нет
● Сертификат         soulmed.uz, 47 дн.
● Диск / память      54% / swap 181 МБ
```

Для каждой строки: цвет, время последней проверки, 7-дневная полоска
(доля зелёных проверок), и по клику — **«что это значит для водителя»**
одной фразой («лимиты июльские: на новых знаках предупреждение будет по
старому лимиту») и ссылка на раздел RUNBOOK «Когда сломалось».

### 4.2. Как устроено

- `server/status.py` (stdlib, как всё остальное) — набор проверок; крон
  каждые 5 минут **заменяет** `healthcheck.sh`. Пишет `status.json`
  (текущее) и строку в таблицу `status_history` в `reports.db` (история для
  полосок, чистится старше 30 дней).
- Проверки ходят **через публичный адрес** `https://soulmed.uz/radarmap/…`
  с `Accept-Encoding: gzip` — путём телефона, а не по файловой системе.
- Подпись проверяется `openssl pkeyutl -verify` тем же публичным ключом, что
  в `AppConfig.otaPublicKeyB64` (в stdlib Python Ed25519 нет; openssl на
  сервере есть).
- Пороги — в одном месте (`status.py`, словарь), с комментарием «почему
  столько».
- Смена цвета → `notify.py` в Telegram, как сейчас.
- `/status` в панели читает `status.json` + историю, ничего не проверяет сам
  (страница не должна тормозить или падать из-за внешней сети).
- Тесты `test_status.py`: на каждую проверку — «зелёный», «устарел»,
  «подпись битая», «gz расходится с json». Класс июльских лимитов обязан
  ловиться тестом.

### 4.3. Что нужно от приложения

Сервер знает, **что** он отдаёт, но не знает, **что дошло**. В анонимную
дневную сводку (`UsageStats`, `POST /api/stat`) добавить версии данных,
которые у телефона сейчас в памяти: база камер, лимиты (v1/v2 и дата),
индекс дорог, индекс MVT, горячие точки, overrides. Никаких координат —
только номера версий, тест на отсутствие `lat`/`track` уже есть. Тогда пульт
покажет «на текущей базе 92% телефонов» и поймает случай «выложили, а
телефоны не берут» (как было бы с неправильной подписью).

### 4.4. Задача для приложения (сервер готов 27.09.2026)

`POST /api/stat` принимает `dataVersions` — словарь из закрытого списка
ключей (`api.DATA_VERSION_KEYS`), всё остальное сервер выбрасывает:

| Ключ | Что слать | Откуда в приложении |
|---|---|---|
| `cameras` | номер базы в памяти | `CameraStore.dbVersion` |
| `limits` | поле `version` загруженного файла лимитов | `SpeedLimitService` (индекс) |
| `roads` | `Int(sha256(payload индекса).hex.prefix(7), radix: 16)` | `RoadNetworkService`, подписанный payload |
| `mvt` | то же по `mvt_index.json` | `EngineTileGuard` |
| `overrides`, `hotspots` | `version` из payload | `CameraOverride…`, `HotspotService` |

В `UsageStats` — поле `dataVersions: [String: Int]`, заполняется при сборке
отчёта. Тест в `UsageStatsTests`: имена ключей закреплены, координат нет.
Пульт («Доставка до телефонов») сейчас серый и оживёт с первой сборкой.
Не сделано в сессии 27.09: не было инструментов Xcode для сборки и тестов.
