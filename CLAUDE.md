# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RadarMap (Xcode project name; product name "RadarMap", bundle `uz.radarmap.ios`) is a native iOS speed-camera map + voice anti-radar navigator for Uzbekistan. SwiftUI on Apple frameworks (MapKit, CoreLocation, CoreMotion, AVFoundation, CoreHaptics, ActivityKit, WidgetKit, MetricKit, CarPlay, WatchConnectivity, AppIntents, CryptoKit) plus **exactly one third-party package** — MapLibre Native 6.29.0 via SPM, which renders the dashboard map from *our own* signed MVT tiles (`Features/Map/Engine/`: `EngineMapView`, `EngineMapStyle`, and `EngineTileGuard`, a `URLProtocol` that sha256-checks every tile against the signed index before the engine sees it). No foreign source: no basemap, no satellite, no network fonts. The whole subsystem sits behind `#if canImport(MapLibre)` and the `engineMap` setting, **Since 11 Oct 2026 the engine is the only base map** — the owner removed the Apple (MapKit) base and the sketch («только новая карта»); MapKit remains for place picking, snapshots and search. Removing the package compiles to a map-less screen that still warns about cameras. It also ships a CarPlay navigator scene and an Apple Watch companion (`RadarWatch`). Paired with a self-hosted VPS backend (camera DB, OSRM routing, speed limits, crowdsourcing API).

**Language convention:** all code comments, user-facing strings, and git commit messages are in Russian. `README.md` is the fullest overview (in Russian). Match this when writing new code, strings, and commits. User-facing text goes through `String(localized:)` and the `Shared/Localizable.xcstrings` catalog (ru + uz); the app also exposes an in-app RU/UZ language override (`AppSettings`).

**`ARCHITECTURE.md`** (Russian) is the companion to this file: it states the layering (MV, no ViewModels) and the 22 coding/review rules the project is written against (errors never swallowed, constants in `AppConfig`, UserDefaults only via `Storage`, network only via `APIClient`, heavy work only via `@concurrent`, silently-applied remote data only via a verified `SignedPayload` and fail-closed, camera alerts never remote-controlled, …). Read it before non-trivial changes.

Single-scheme project (`RadarMap`). Five targets: the app (`uz.radarmap.ios`, which also hosts the CarPlay scene), `RadarMapWidgets` (`…ios.widget` — Live Activity + home widget), `RadarWatch` (`…ios.watch`, watchOS companion, deploys **watchOS 11.0**), `RadarWatchWidgets` (`…ios.watch.widgets` — the watch-face complication, embedded in `RadarWatch`), and `RadarMapTests` (`…ios.tests`, XCTest). They must stay on one team: the app target used to sit on a personal team, and a personal team can register neither App Groups nor CarPlay, so every device install meant hand-editing the bundle id and emptying entitlements. ## Architecture

### Dependency injection
`AppEnvironment` (`App/AppEnvironment.swift`) is the composition root — a single `@MainActor @Observable` object, `AppEnvironment.shared`, built once and shared by the phone SwiftUI scene *and* the CarPlay scene (CarPlay may connect before the SwiftUI scene). Injected via SwiftUI `.environment(...)`, read with `@Environment(AppEnvironment.self)`. It owns every service and **wires cross-service callbacks in its `init`** (e.g. `MotionService.onDrivingStart` → start trip; `RouteService.onManeuver` → speak). To understand how a feature is triggered end-to-end, read this `init` first — the services themselves are decoupled and only know about closures.

### Concurrency model
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` + `SWIFT_APPROACHABLE_CONCURRENCY = YES` (Swift 5 language mode). Nearly everything is implicitly `@MainActor`. Because approachable concurrency turns on `NonisolatedNonsendingByDefault`, a plain `nonisolated async` runs on the **caller's** actor — so `Task { await Self.heavy() }` from the main actor stays on main. To actually get off main, heavy work is marked **`@concurrent`** (see `CameraRepository` DB decode, `JSONFile`); stateless utilities (`Log`, `JSONFile`) are `nonisolated enum` so a call from `@concurrent` code doesn't hop back to main. Pure geometry helpers are `nonisolated static`; some still run via `Task.detached` (`RouteService.apply` cameras-along-route, `SpeedLimitService`). `CLLocationManagerDelegate` callbacks are `nonisolated` and hop to `@MainActor` via `Task { @MainActor in ... }`. (See ARCHITECTURE.md rule 11.)

### The heart: `LocationService`
This is the most important and most complex file. It runs **two GPS modes**, selected centrally in `applyLocationMode()`:
- **Silent background** — significant-location-change + up to 20 `CLCircularRegion` geofences (iOS hard limit) around the nearest cameras; the system wakes the app on region entry → local notification. Near-zero battery.
- **Trip mode** (`startTrip`/`endTrip`) — continuous high-accuracy GPS with active alerts even when backgrounded (requires "Always" auth). Auto-started/stopped by `MotionService` (CoreMotion) when `settings.tripStartMode.usesMotion`. `TripStartMode` (`auto`/`smart`/`manual`) replaced the old `autoStartTrip` toggle — `.smart` additionally requires the driver to be recognized (`isDriverRecognized`, from saved places and prior confirmations) and otherwise asks, so a passenger's phone doesn't record a trip.

**Outside a trip a geofence entry is not proof of driving** (stage 26, 21 Oct: the owner got «Камера через 550 м» at home — the region is armed with radius `alertRadius`, the system decides «entry» from Wi-Fi/cell positions off by 100–500 m, a phone lying 550 m from a camera crosses the edge on jitter, and exit used to clear the dedup so every jitter cycle pushed again). `handleEnter` now hands the camera to `QuietAlertGate` (`Models/`, `QuietAlertGateTests`): within a ~10 s background window it reads CoreMotion history (`MotionService.recentMotion`, works without monitoring) and a one-shot `Best` fix, and notifies only on proof — CoreMotion «in a car» (a car that stopped ≤ 3 min ago counts: red light), a satellite fix with car doppler, or two fixes displaced beyond 2× their accuracy and ≥ 400 m at car speed; silent when standing/on foot, at Home/Work (manual + learned, persisted) without CoreMotion's car, on a fresh precise fix far outside the circle, for the same camera within 20 min (log in `Storage.quietAlertLog`, survives the process), and in «Только в машине» without the car. The rule is the inverse of the trip pipeline on purpose and the trip pipeline is untouched. **`TripStartMode.carOnly` «Только в машине»** (`Models/CarLink.swift` + `CarLinkService`, `CarLinkTests`): a trip starts when CarPlay or a Bluetooth device chosen in Settings → Поездка → «Моя машина» (`AppSettings.carDevices`, uid then name) connects and ends `carLinkStopGraceSeconds` (2 min) after it disconnects (`endTrip(auto:)`, so TripMerge glues the gas station); no CoreMotion. CarPlay wakes the app itself; Bluetooth does not — the route is re-read on every quiet-background wake (SLC fix, geofence, opening), so a BT start lands on the first wake, usually within the first 0.5–1 km. People who ever had CarPlay (`Storage.carPlaySeen`) get the mode offered once (settings card + one-time map hint), never switched silently. Also from 26.3: «Я за рулём» no longer learns headphones as a car (`CarLink.looksLikeHeadphones` — AirPods in `knownCarAudio` made every taxi ride «own car»), and «Авто» with a chosen car device asks instead of silently recording a ride without it. DEBUG: `-carLinkDemo` (fake BYD + AirPods ports), `-carOnlyDemo`, `-carOnlyOffer`.

Behavior the user can steer lives in `AppSettings` as small enums, each with its own title/symbol: `AlertMode` (auto / city / highway — overrides `AlertPolicy`'s detector), `TripStartMode`, `BackgroundAlertMode` (all / radars only / off), `CameraFilter`, `MapAppearance`, `AppLanguage`.

`LocationService` is an orchestrator: nearly all the decision logic lives in **pure, tested `nonisolated` engines** it calls in a fixed order (see the pipeline below). It keeps for itself only what needs the live `CLLocationManager`: adaptive accuracy (relax GPS when far from cameras/maneuvers — `tuneAdaptiveAccuracy`; the old cruise-tier boost for the CarPlay sketch went with the sketch), geofence retiling, the stale-fix watchdog, driver/passenger recognition (`confirmDriver`/`markPassenger`), trip stitching on start (`resumePreviousTripIfMerged`), and CoreHaptics escalation via `AlertPlayer.haptic(level:)`. Speed-limit matching and route progress are driven from here (not the UI) so voice keeps working when backgrounded. The speedometer value goes through `SpeedSmoother` (pure, tested): time-based EMA that snaps immediately on a real >6 km/h change — constant weights on the irregular adaptive-GPS tick rate used to drag a braking tail for 5+ seconds. Since 21.10 (25.C, CarPlay «3 км/ч» at a stop line) the whole number is one pure model, `Models/Speedometer.swift` (`SpeedometerTests`: traffic light, noise on the spot, 10 s without fixes, a 5 km/h crawl that must never read 0, CarPlay without a trip): `Standstill` also enters on Doppler *noise* (< 8 km/h, but the position moved < 0.4 of the path the Doppler promised, or the Doppler is within its own `speedAccuracy`, or CoreMotion already says stationary) — the old «every fix < 3.5 km/h for 2 s» never held under 2–8 km/h noise — and leaves on one fix beyond 3σ (a number ≤ 1 s after moving off); `SpeedBound` zeroes a low speed (< 15) after 2.5 s without Doppler (any filter below 8 km/h, else after 1.5 fix intervals), and fixes without speed no longer restart the decay. Below 8–15 km/h nothing in the alert pipeline reads the number (base radius, voice from 20), and a pass takes the zone minimum, so the earlier zero cannot add a violation.

### The alert pipeline (read this before touching alerts)

Every GPS tick runs through four engines in this order. **The governing rule is asymmetric: silence about a real camera is worse than one extra warning**, so each gate may only mute a camera when it has positive proof the camera is *not* ours; unknown data means warn. Six separate "why was it silent" bugs came out of violating that. The ordering itself now lives in **`Services/LocationGates.swift`** — a pure `nonisolated` module taking a six-field `Situation` plus an externally-supplied "is it on the route" answer — with `LocationGatesTests` pinning the policy (before the extraction the order could only be verified by reading `LocationService` next to a live `CLLocationManager`).

1. **`LocationFilter`** (`Services/`) — the fix-quality gate, ahead of everything. Rejects cached/jumped/inaccurate fixes before they reach alerts, track, or stats (a stale first fix used to register as a real camera pass at a bogus speed, since `PassTracking` takes the zone minimum). It also owns **course trust**: raw `course` only when `courseAccuracy` says so, else course-over-ground from the most recent accepted fix at least 12 m back within 5 s — both fixes ≤ 25 m accuracy and the step at least their summed accuracy (13.3, 14.13: at city speeds the gates used to be off entirely, and Wi-Fi-quality 60 m fixes produced a sideways «course» that muted our own camera) — else `-1` — which switches the directional gates off entirely rather than letting a bad course mute a real camera. Works on a plain `Fix` struct, no `CLLocation`.
2. **Direction / road-shape gates** — `RoadShape` + `RoadGeometry` (`Models/RoadShape.swift`) wrap the per-camera road data shipped in the DB: `dir` (one-way carriageway heading), `axis` (undirected 0–179°, catches driving *over* a camera on a bridge or across an interchange), `cls`/`lanes` (lane half-width instead of one global constant), and `road` (a short polyline of the camera's own carriageway, so "am I on this road" is a real distance to a line, and the axis is taken at the camera's point instead of one axis for a curved road). Muting by direction requires `Camera.allowsDirectionGate` — i.e. `sidesAreProven` (a twin camera facing the other way, or a road known not to be divided). About half the DB cannot prove it, and those cameras may well shoot both sides, so they are never muted this way. `hasTrustedRoadProfile` throws out cameras the snap landed on a footway/crossing/platform (39 in v10) — their "road" says nothing about traffic.
3. **`RoadCorridor`** — the fallback heuristic that replaced the old ±70° cone (at 400 m that cone accepted a camera 375 m sideways, i.e. every parallel street and overpass). It splits the vector to the camera into along-course and lateral components and decides on **lateral offset in metres**: narrow near the car (course is trustworthy, curvature has not accumulated), widening farther out by a small cone so a camera on your own highway past a bend survives. `isAhead` is now just `RoadCorridor.fix(...).along >= -corridorBehindToleranceMeters`. Crowdsourced/sudden points and `needsReview` cameras get the generous highway corridor.
4. **`AlertEngine` → `AlertPolicy`** — `AlertEngine` decides *whether* to fire (escalating levels 1–3 with hysteresis; `effectiveRadius` is the "smart radius" — warn N seconds out, not fixed metres; `isFirst` is tracked separately from `level == 1` because a camera can first be seen late). `AlertPolicy` then decides *how loud*: a city/highway `Detector` (votes from road class, camera density, and an EMA of speed, with a switch cooldown) feeds a three-grade `Style` — `silent` (HUD + one soft tap), `brief` ("Камера, 300 метров" — city, cameras come one after another), `calm` (full phrase with type and side — highway), `urgent` (siren + escalation: sudden points and sustained overspeed at a camera). One uniform shout for every camera is functionally the same as no warning at all, which is what this exists to prevent.

**The camera shown is not always the camera alerted** (25.I, 21 Oct, `Models/NearestDisplayHold.swift`, `NearestDisplayHoldTests`). Below `directionalMinSpeedKmh` the gates abstain, so the alert camera (`nearestCamera`/`distanceToNearest`, chosen by `LocationGates.nearestOursIndex`) becomes the nearest of any kind — a side street 140 m off — and in a 5↔12 km/h jam the HUD, chip, watch, Live Activity and map flickered between two cameras. Display surfaces read `displayNearestCamera`/`displayDistanceToNearest`: below the threshold they keep the last «ours ahead» camera for `nearestDisplayHoldSeconds` (60 s since the last gated tick) while it is within `nearestDisplayHoldMaxMeters` and still passes the same gates with the current trusted course (else the last one) — a real turn releases it at once, a long stop falls back to the old behaviour, and a released hold does not return until the next gated tick. Not a 10/6 km/h speed hysteresis: that would still flicker at 5 km/h. Alerts, levels, voice, the full-screen alert and the CarPlay banner keep reading `nearestCamera`; the hold only acts where `isApproachingCamera` is false anyway, and a test replays jam/turn/stop/pass through the old and new selection and `AlertEngine` and requires identical decisions. `CarPlayOverlay`'s dock cell still reads `nearestCamera` (switch it to the display pair).

`PassTracking` closes the loop after the fact: it records the minimum speed in an 80 m measurement zone (`passZoneMeters`) at each camera's traverse point, radar-style, feeding «Итоги».

**The record is gated differently from the alert, and that asymmetry is deliberate.** An alert fires on suspicion — one extra beep is cheap. A recorded pass costs a false violation, a wrong hotspot in «Где теряете баллы» and rating points, so it demands proof. Two gates run at the *traverse point*, not at acquisition: the traverse distance (`passTraverseMaxMeters`, 40 m for snapped cameras; 80 m for hand-placed ones whose coordinate never went through the snap), and `PassGeometry.isProvenOffRoad` — the lateral offset from the camera's own carriageway (`road`, present for 99.7% of the DB) against `RoadGeometry.halfWidth`. Checking at the traverse is the whole point: the alert corridor is widest exactly where it is evaluated on approach (68–93 m of lateral tolerance at 400 m), so a camera on the crossing street of an interchange used to slip through acquisition once and then ride all the way into history. `isProvenOffRoad` returns false for "no proof" — on intersections OSM cuts the way into 20–30 m stubs and `lateralOffset` correctly gives nil. The distance gate does not catch that case (camera 2676 on Rustaveli was recorded from Bobur at 17 m, run 13.3), so a third gate does: `PassGeometry.isProvenCrossing` — the median deviation of the trusted course from the camera's road axis over the ticks within the traverse limit exceeds `passCrossingMinAngle` (45°, deliberately stricter than the alert's 55°: a lost record is cheap, a foreign junction in the rating is not). Only for `profileMayMute` profiles with a verified position and fixes no worse than `courseProofMaxAccuracyMeters` (25 m — course over ground on Wi-Fi-quality fixes is noise); no course or crawling means no proof. `TripHistory.sanitized` (`passCleanupMaxMeters`, 70 m — the live gate plus track simplification) is the retro version for history already on disk; it runs once per `Storage.passGeoCleanupN` flag and must repair the daily rollups surgically (`unfolded` old + `folded` new), never by rebuilding `days` from history — that would erase the months whose records are long pruned.

### `RouteService` — routing (own engine)
Apple Maps does not route inside Uzbekistan, so `calculate()` tries `MKDirections` first and falls back to the **self-hosted OSRM server**. Produces engine-agnostic `Variant`s (each with cameras-along-route count and turn-by-turn `RouteStep`s). Live progress (`updateProgress`, called per GPS tick) handles arrival detection, next-camera/next-maneuver, voice maneuver staging, and off-route reroute (with GPS-noise confirmation ticks + cooldown). All the geometry (`project`, `camerasAlong`) is `nonisolated static` and runs off-main.

**Off-route is three rules in `Models/RerouteGate.swift`** (pure, `RerouteGateTests`), one cooldown/backoff for all: far (`rerouteDeviationMeters`, 3 fixes), sustained drift (20.6) and, since 20.9, **wrong way** — a trusted course on the move (≥ `directionalMinSpeedKmh`) more than `rerouteWrongWayDegrees` against the segment *the projection picked* (`segmentHint` after `project`, which already penalises opposite segments) for `rerouteWrongWayTicks` fixes while progress retreats `rerouteWrongWayBackMeters`. A U-turn on the route's own street left the car 5–30 m from the line, so neither distance rule ever fired and the route led backwards to the destination; a loop that legitimately returns along the same street is on its matching branch and stays silent. A confirmed wrong way also sets `isOffRoute` (route-remaining to cameras means nothing then). The projection window ahead is measured from the *end* of the hint segment (20.9): from its start, a straight highway segment of 400+ m kept the next one out of the window, the deviation grew to 200 m past every such node and the 20.6 drift rule rerouted on a straight road. Every route request from the current position sends the heading too, not only reroutes: `build`/`addStop`/`removeStop`/`replaceOfflineRoute` take `heading: LocationService.routeHeading` — the trusted course only while moving (`RouteService.requestHeading`), standing means no heading (the driver may go either way). `MKDirections.Request` has no heading; inside Uzbekistan Apple does not route, so the bearing reaches OSRM. A request that never reached OSRM (`RouteError.noConnection`) is not retried without the heading — that would double the 12 s timeout.

**The last 1–2 km of the ETA** (`Models/ArrivalTail.swift`, `ArrivalTailTests`, 21.10): the engine remaining time is a linear share of OSRM's free-flow time, which in town promised «arrival now» for 0.7 km at 10 km/h; within `arrivalTailFromMeters` the remaining time is blended (0 at 2 km → 1 at 1 km) toward remaining ÷ our time-weighted average speed over the last 2 min (stops at lights count, floor 12 km/h), and only ever later, never earlier. `personalRemaining` (the commute ghost) is untouched and `engineRemaining` stays raw for detour comparisons. A U-turn onto the street we are already on is «развернитесь», not «разворот на улицу Беруни» (`maneuverStep(currentName:)`).

**Choosing a variant** is `Models/RouteChoice.swift` (pure, `RouteChoiceTests`), Yandex-style labels without the server: «Знакомый» (share of the variant covered by the driver's own past tracks on a ~30 m grid, start/end excluded, needs 3+ trips and a clear margin over the other variants), «Быстрый», «Меньше камер», «Спокойнее» (no cameras where the driver overspeeded — the same measure as `CameraFamiliarity`), «Проще» (fewer left turns/U-turns/roundabouts, judged only when every engine named its maneuvers) and «Короткий». A familiar variant is selected first when it costs at most max(3 min, 10 %) over the fastest. Rules, not a model: every label explains itself in one line under the chips (`RoutePanel.reason`). History comes through `RouteService.personalHistory` (wired in `AppEnvironment`, off via Settings → Маршрут → «Учитывать мои поездки»); nothing leaves the phone. No «Без пробок» until there is an honest traffic source. Reroutes carry no labels.

**«Моя дорога»** (24.4, `Models/MyRoad.swift`, `MyRoadTests`; owner 21.10: «каждый день по своей дороге возвращаюсь домой, а он предлагает другой вариант») — when the destination is within 300 m of Дом/Работа and that direction has a `CommuteProfile` variant with 3+ trips ending at it and starting ≤ 1 km from the car, `RouteService.build` sends, alongside the normal request, one more OSRM request through 3–8 pass-through via points taken from the variant's line (60 m past turns ≥ 30°, mid-points of straights ≥ 900 m, never on a leg < 120 m, ≥ 400 m apart, none within 300 m of home/work or of the line's ends; `waypoints=0;N` so there is one leg, `continue_straight`, a bearing ±45° and a 50 m radius per via so it takes our carriageway). The result is dropped if it is > 15 % longer than the line (a U-turn at a via) or overlaps it < 80 % either way; an engine variant that already overlaps the line ≥ 80 % both ways is labelled instead of adding a duplicate; otherwise it takes the slowest engine variant's slot (≤ 3 chips). Label `.myRoad` ranks above «Знакомый»; its time is the driver's own time for this hour — the same calibrated base as the ghost (`CommuteGhost.select` + `calibratedBaseline` with the journal bias in `Plan.bias`, stage 24.2; `baseline.usualRemaining` from the start's projection) plus crowd jams above 1.25× own median (`CommuteEstimate.jamExtra`), shown as the chip ETA (`Variant.expectedTime`/`shownTrafficDelay`); it is recommended first when that is ≤ fastest-with-traffic + max(3 min, 10 %) (`RouteChoice.isAffordable`). Reason line: «так вы ездите домой — обычно 39 мин»; CarPlay's trip preview reuses `RoutePanel.title/reason`. «Знакомый» now also counts the profile lines (45 days, weighted by trips, minus trips whose track is still in history) via `History.commuteLines`. Off with «Учитывать мои поездки» or «Время дороги на работу»; no offline-graph variant (it takes no via points). A reroute while «Моя дорога» is selected goes through the via points still ahead by projection (`MyRoad.remaining`: the nearest one is skipped when < 300 m away or > 100° off the course; > 1 km off the line or none left → the engine), with the same loop rejection, keeping the label and own-history time. DEBUG `-demoMyRoad` seeds the choice without network.

### `CameraStore` (`CameraRepository`) — data
Merged set = bundled `Resources/cameras.json` + user-added `custom` + crowdsourced `mobile` − `hiddenIDs`. Two caches invalidated together in `dataChanged()`: a `mergedCache` list and a **grid spatial index** (0.05° ≈ 5.5 km cells) so `nearest(to:)` and `cameras(in:)` never scan all 3511 cameras on the hot path (retile fires every ~1.5 km driven). `revision` increments on any change; UI observes it.

The bundled DB is **v12** (`AppConfig.bundledDBVersion`, 3511 points from data.egov.uz 1-008-0027 — v11 plus 36 registry places of 25.08.2026 — snapped to the OSM road axis; the 20.10 registry diff — 148 DB cameras missing from the registry, 77 new points — waits for the owner in `server/review/registry_diff_2026-10-20.csv`, never remove by that list). A new registry pull is **appended, never rebuilt**: camera ids live in the user's own data (passes in trip history, familiar cameras, hidden ones), so v11 is byte-identical to v10 for its first 3467 records and the 8 new addresses got ids 3496–3503. The profile for a new point is derived by the same `snap_cameras` code, off an OSM extract around it — running the full VPS snap for eight cameras buys nothing and risks moving 3467 that are already right. Beyond the base fields, each camera may carry the road profile the alert pipeline runs on — `axis`, `dir`, `lanes`, `cls`, `road`, `split`, `twin` — all optional, all `nil` on older records (`bridge` was dropped on 20.10: it never fed a gate), which is why `Camera` exposes the derived guards `sidesAreProven`, `hasTrustedRoadProfile`, and `allowsDirectionGate` instead of letting call sites read the raw flags. `violations` is omitted in the bundled JSON and reconstructed from the type via shared static arrays (one copy in memory for all cameras).

OTA updates (`applyRemote`) verify an **Ed25519 signature** (`Support/OTASignature.swift`, public key in `AppConfig.otaPublicKeyB64`) before anything else — an unsigned or bad-signature payload is never applied (fail closed), which is what makes shipping the DB over plain HTTP acceptable until the HTTPS move. Then it validates, atomically writes `Documents/cameras_remote.json`, and swaps in memory; the downloaded copy survives app updates and is preferred over the bundled DB on next launch. The bundle is **v12**; production gets a version only when the owner deploys it (check `version.json`) — until then OTA simply answers «нет обновлений». Publishing stays manual: the signing key never leaves the owner's machine, so a DB reaches prod by hand or not at all, and a bundle bumped without a deploy just means the app answers "нет обновлений" — correct, since `RemoteSyncService` applies a payload only when `manifest.version > store.dbVersion`.

### Remote control: four signed files, one verifier

Everything the server can hand the app is applied **without the user's
involvement**, so all of it goes through one `Support/SignedPayload<T>`:
Ed25519 verified *before* the JSON is parsed, and any defect at all — missing
signature, foreign key, malformed JSON, out-of-range value — means falling back
to the build's own values, never the received ones (ARCHITECTURE.md rule 19).

- **`cameras.json` + `version.json`** — the camera DB itself (`RemoteSyncService`).
- **`config.json` — «пульт»** (`RemoteConfig` / `RemoteConfigService`, checked every 6 h).
  Can disable routing, crowdsourced reports and metrics, change the poll
  interval, and show an announcement or an "update required" banner. It
  **cannot touch camera alerts** and never will — the DB is local, the warning
  must work with no server at all, so it must not depend on what a server sends
  (rule 20). The cached pult survives a relaunch (otherwise it is not a kill
  switch) but expires after `remoteConfigMaxAge`, and a fetched-in-the-future
  timestamp is distrusted. Published by `server/publish_config.sh`.
- **`overrides.json`** — the moderator's decisions over the DB
  (`CameraOverride` / `CameraOverrideEngine`, checked every 3 h): `hide`,
  `move`, `retype`, applied to the bundled set only, ahead of `custom`/`mobile`
  in `CameraStore.cameras`. 2 KB instead of a 1 MB DB, so it ships daily and a
  rollback is "publish the file without that line". Three safeguards, because
  hiding a camera produces **silence where a camera stands**: the signature; a
  file hiding more than `overrideMaxHiddenShare` of the base is rejected
  wholesale (protection against a typo in SQL, not against an attacker); and a
  move farther than `overrideMaxMoveMeters` or outside Uzbekistan is dropped
  while the camera stays put. A moved camera loses its whole road profile
  (`axis`, `dir`, `road`, `split`, `twin`) — the snap measured those at a
  *different point*, and `road` is stored as deltas *from* the camera, so it
  would have travelled along. The cost is that the camera warns more often,
  which is the side to err on. Published by `server/publish_overrides.sh`.
- **`speed_limits_index.json`** — the speed-limit set (`LimitsManifest` /
  `LimitsTrust`, `SpeedLimitService`, checked weekly). Limits speak
  («Превышение скорости») and price fines, so they are in the same trust class
  as the DB. Built like road tiles: the signed index carries `name`/`sha256`/
  `bytes` of each limits file, the 3.4 MB file itself travels unsigned and is
  sha+size-checked against it; the verified envelope is cached next to the
  data and both are re-verified on **every** load from disk
  (`SpeedLimitCache`). Files live under content-addressed names
  (`limits/speed_limits_v2.<sha16>.json`) because the monthly cron rewrites
  `speed_limits*.json` in place — old builds keep reading those. **Transition
  ratchet:** until a phone has seen one genuinely signed index it falls back to
  the old unsigned files (the owner had not published yet, and an update must
  not take limits away); the first valid index sets `Storage.speedLimitsSignedSeen`
  and the unsigned path is closed for good — a missing/invalid index then means
  "keep the last verified set, else no limits", never "take what is served".
  `AppConfig.speedLimitsAcceptUnsigned` closes the legacy path for phones that
  never saw an index; flip it to `false` once the owner has published.
  Published by `server/publish_limits.sh` (after each monthly limits cron —
  `/status` shows «ждёт подписи» until then).
- **`lanes/lanes_index.json`** — the lane overlay (20.8, contract
  `docs/lanes_overlay_contract.md`; `LanesManifest` / `LaneOverlay` /
  `LaneOverlayTrust`, `LaneOverlayService`): lane rows for maneuvers and
  straight-through junctions where OSRM has no `turn:lanes`. Same shape as
  the route graph — signed index, sha+size-checked `lanes.<sha16>.json`,
  both re-verified on every disk load; weekly (daily while the server answers
  404), first file over any connection, updates not over cellular, an older
  signed version is a rollback and is refused. Loaded into memory lazily by
  the first route. `RouteService` collects `LaneProbe`s while parsing OSRM
  (approach bearing from the route line over the last 30 m) and
  `LaneOverlay.attach` fills only steps/junctions without OSRM lanes —
  OSRM always wins; a row with no lane fitting the maneuver is dropped (edge
  advice stays). Re-attached on overlay arrival/removal; one log line per
  route «полосы: OSRM N, слой M, край K (…)». Kill switch `features.laneOverlay`.

### Other services
- `RemoteSyncService` — daily OTA check of the camera DB against the server `version.json` (version + sha + signature), plus the `overrides.json` fetch on its own 3 h cadence.
- `ThermalService` / `PerformanceMode` — reaction to `ProcessInfo.thermalState`. A phone in a windscreen mount under the Tashkent sun reaches `.serious` in 15–20 minutes and iOS cuts the CPU itself; the app used to keep asking for the same work, which is exactly what a user calls "лагает" and what a simulator never shows. `.reduced` cuts the annotation budget to a third, drops heat lines and recomputes the map layer half as often; `.minimal` goes to an eighth and a quarter. What gets cut is a question of priorities, not thrift: behind the wheel voice beats picture, so decorations go first and camera alerts are never touched. The budget never reaches zero — a camera stays a marker or part of a counted cluster, but never vanishes.
- `RoadNetworkService` — the signed road set (see `server/build_roads.py` below): a signed index verified on **every** load including from disk, and sha256-checked files behind it. Its live consumers are search (per-city `AddressBook`/`VenueBook` files), «Радар!» report snapping (`reportNetwork` — street tiles UNION the limit-index axes, since yards are not in the street set) and the CarPlay junction sketch (`vehicleNetwork` — tiles, else the limit index). Only the street set is fetched, 3×3 around the car, from `ensureCoverage` on trip/CarPlay/probably-driving fixes (19.10 — after the sketch went on 11 Oct nothing requested coverage and reports went out as the raw driver coordinate). The server republishes files under the same names while a phone re-checks the index every three days, so a file whose sha disagrees with the cached index triggers an immediate index re-check (≤ once per `roadsStaleIndexRecheck`) — before that, the whole neighbourhood was marked broken for days.
- `NetworkMonitor` — one fact (`isOnline`) for one honest sentence. Map tiles need the network; the camera DB does not. On the Tashkent–Bukhara road the map goes grey while warnings keep working, and the difference between "приложение сломалось" and "карта не грузится, но я предупреждаю" costs one banner.
- `UsageStatsService` / `UsageStats` — the anonymous daily aggregate (`POST /api/stat`). Counters only: trips, km, alerts, passes, reports, screen opens, plus app/iOS/model and the **location-authorization level** — the single most important number in the product, since without "Always" neither background alerts nor trip auto-start work. No coordinates, no routes, no event timestamps (a test encodes a report and greps it for `lat`/`track`/`timestamp`). Off via a Settings toggle *and* via the pult, on the same 30-day rotating UUID as everything else.
- `MobileCameraService` — crowdsourced mobile-radar reports; polls every 3 min in foreground **and every 75 s for the whole trip, screen off included** (`setTripActive`, wired from `LocationService.onTripStateChanged`) — a tripod stands for an hour, and a report that reaches the driver three minutes late finds them already past it; the pult stays above this, so an interval it deliberately widened is never undercut by a trip. The phone still never tells the server where it is: it takes every live marker (a handful nationwide) and decides for itself what is on its way. **the driver's half of the loop lives here too**: `quickReport` behind `ReportGuard` (one blind tap from the trip bar, the dashboard or CarPlay — refusing a double tap, a same-spot repeat within 3 min / 400 m, and a report from the couch, while letting a report through when standing in traffic *during* a trip), and `MobilePassWatch`, which asks «радар ещё стоял?» exactly once and only after the driver passed within 90 m and left by 180 — silence sends nothing, because «не знаю» corrupts the data worse than absence (the answer is voiced a thank-you and ships with `kind=pass` so moderation can tell a real-pass vote from a couch tap). The prompt waits while a camera alert covers the screen; anonymous device UUID from `Storage.anonymousID`, which **rotates every 30 days** so reports can't be chained into a long-term trace. The server-side trust lifecycle surfaces here too: an unconfirmed report renders as a **ghost marker** (translucent, dashed, «?») and the voice names the source — «Отметка водителей: тренога впереди…» — warn always, but don't sell a rumor as a fact; attribution beats a bare «возможно» because it says where the point came from and makes the community visible, which is how a driver learns their own taps work (`Camera.mobileConfirmed`, nil for the old server keeps the old look). Right after a quick «Радар!» a 6-second `ReportRefineBar` («Что это было?» — тренога/пост/ДТП) lets one tap retype the *same* point via the server's amend; silence honestly leaves «радар».
- `HotspotService` / `TripodHotspots` — **«здесь часто ставят треногу»**. The dislocation schedule for mobile radars is approved daily by the regional traffic-safety chief and is not published — since 2022 a driver cannot even see it at the roadside. But its points repeat, so the reports drivers already send are that schedule rebuilt from below, and nobody else has it. `server/build_hotspots.py` clusters 90 days of radar/tripod reports at 200 m and keeps only what **different people** vouched for (3+ reports, 2+ devices **and** 2+ addresses — one stubborn driver marking the same spot daily must not make the app lie to a city); the payload carries coordinate, counts and a quarter-of-day, never a device, an address or a timestamp, because those reconstruct someone's route. Signed by the owner (`publish_hotspots.sh`), verified through `SignedPayload` on **every** load including from disk, fetched weekly, fail closed to no hints at all.
  The tone rule here is the **inverse** of the camera rule, deliberately: a camera warns on suspicion because silence is worse, but this is a guess about the past, and a guess sold as fact costs trust in the whole app. So no course, no limit, or not speeding all mean silence — while the zone still renders on the map, because showing and saying are different things. `HotspotAlert` (pure, `TripodHotspotsTests`) holds that decision; the voice is one calm line per spot per trip, and the map draws a dashed translucent band, never a camera pin, and only at close zoom.
- `SpeedLimitService` — matches OSM `maxspeed` for the current road (position + course), warns on overspeed with a tolerance; ~3 MB DB, indexed for microsecond per-tick matching. Loaded only through the signed index + ratchet above (`LimitsTrustTests`).
- `RoadWeatherService` / `RoadWeatherAlert` (19.2) — «На перевале Камчик туман». Reads `weather/roads.json` (server `build_road_weather.py`, open-meteo) with ETag every 30 min while a screen, CarPlay or a trip is on; a file older than 2 h is no data. The pure `RoadWeatherAlert` (`RoadWeatherAlertTests`) says one calm phrase per pass (point `group`) per trip: on a route — points ≤ 1 km from the line ahead, by route distance; without one — only on a highway, moving, with a trusted course, in a corridor widening with range; window up to 40 km (normally 20–40, closer is still said once, inside the stretch never); only hazards that will meet the driver (now or within the hour). A camera ahead (`isCameraBusyForRoadNotes` — the road-event rule) makes it `.wait`, never drop. Banner: phone `RoadWeatherBanner`, car `CarPlayRoadWeatherBanner` in `CarPlayBanners` as `.roadWeather` (below camera, detour and driver request, comes back). Kill switches: Settings → Оповещения → «Погода на перевалах», pult `features.roadWeather`. Display data, unsigned, never touches camera alerts (rule 20).
- `AlertPlayer` — preloaded beep + `AVSpeechSynthesizer` (plays over silent mode, ducks other audio) **plus CoreHaptics**: `haptic(level:)` fires a distinct pattern per alert level instead of one generic buzz.
- **Recorded voice (stage 16)** — `AlertPlayer.speak(_:event:)` is the one switch point between a native speaker's recording and the synthesizer; call sites and timing are unchanged. A phrase is a typed `VoiceEvent` (camera, maneuver, limit ahead, jam, detour, hotspot, fixed phrases — the latter found by text via `VoiceText.index`, so most call sites pass no event), `VoiceComposer` turns it into recorded segment ids per language (uz/ru: own word order, suffixed forms as their own recordings, numbers 1–299 from tens+units, distances in recorded steps 50…900 m, 1, 1.5 km). `RecordedVoice.plan` plays the recording only if the voice setting says so, the pack has EVERY segment and `VoiceText.render(event)` equals the caller's text exactly — anything else (street name, missing/corrupt file, decode or engine failure in `SegmentPlayer`) speaks the whole phrase through the synthesizer: never silence, never half a phrase. `SegmentPlayer` (AVAudioEngine, audio-session queue only) joins decoded, edge-faded buffers sample-exact with synthesized pauses; same session/`promptStyle`, one FIFO with the synthesizer (never both at once) and a stall watchdog. The pack is `RadarMap/Resources/Voice/voice-uz.bundle` (manifest + AAC, sha256 per file, ≤ 3 MB); the `say`-generated `voice-uz-placeholder.bundle` (`placeholder: true`) is DEBUG-only (switch in alert settings or `-voicePlaceholder`; `-voiceDemo` speaks a sample) and excluded from Release by `EXCLUDED_SOURCE_FILE_NAMES`. The setting «Голос оповещений» appears only when a pack exists. Speaker kit, validation and pack build: `tools/voice_kit/` (README in Russian; the script CSV is exported from code, a test keeps it in sync).
- `WatchBridgeService` — pushes the trip HUD (speed, next-camera, alert level) to `RadarWatch` over `WatchConnectivity`; the watch escalates with wrist haptics.
- `FeedbackService` — in-app feedback form submission (see `Features/Settings/FeedbackFormView`).
- `CameraDirection` — "smart direction to camera": prefers the route heading, falls back to a smoothed course, with a wide dead zone to avoid flip-flopping.
- `LiveActivityService` / `MetricsService` (MetricKit) / `NotificationService` (one updatable notification per trip, not a stack).
- `App/RadarIntents.swift` — App Intents for Siri / Shortcuts / the Action button; "Начать поездку" runs without opening the app (background launch + "Always" auth is enough to start continuous GPS).

### Configuration
**`Support/AppConfig.swift` is the single source of truth for all tunable constants**, grouped by `// MARK:` sections that mirror the pipeline: alerts/geolocation, the city-highway detector thresholds, GPS fix quality (`LocationFilter`), the camera's road (direction, lanes, road shape), map, pass map, directional alerts, road corridor, trip stitching, OTA, routing, CarPlay. Change behavior here, not scattered across files. Server base is `syncBaseURL` — **`https://soulmed.uz/radarmap`** since 11.08.2026 (OSRM at `/osrm`, API at `/api`, panel at `/admin/`). The move to HTTPS removed `NSAllowsArbitraryLoads` from `Info.plist`. The domain belongs to another project on the same VPS and is wired in by a single `include` line inside its nginx server block, so a rollback is deleting one line; `server/HTTPS.md` documents the whole layout. The old `http://45.130.148.94:8090` stays alive in parallel — a build with the old address may already be in App Store, and switching it off would break it unfixably.

The rest of `Support/` enforces the ARCHITECTURE.md rules and is where the shared plumbing lives, so use it rather than reinventing:
- **`APIClient`** — the only place that touches the network (base URL, per-request/resource timeouts, status check, JSON en/decode, logging). Services describe *what* they want, not *how* to make the request.
- **`Storage`** — typed `UserDefaults` access; every key is a case in one enum, no raw string keys in code. `AppSettings` is the one exception (its own typed `Keys` façade).
- **`Log`** — `os.Logger` split by subsystem (`Log.alerts`, `Log.sync`, …); a `nonisolated enum` so `@concurrent` code can log without hopping to main. Errors are logged, never silently `try?`-swallowed.
- **`Perf`** — `os_signpost` wrappers (DEBUG-only, subsystem `uz.radarmap.ios` / category `perf`) around the hot paths: `handleLocation`, camera-layer build, rating screen, and a `mapBody` *event* counting MapScreen body rebuilds. Profile with Instruments → os_signpost track; release builds compile to nothing.
- **`Wiring`** — `assertSingleAssignment` for the `onX` callback hooks wired in `AppEnvironment.init`. A plain closure property silently loses its first assignment on a second one — that exact bug shipped a dead weekly-digest block — so every hook's `didSet` now traps a re-wire in DEBUG.
- **`JSONFile`** — atomic JSON read/write off-main; **`OTASignature`** — Ed25519 verification of the OTA DB; **`Concurrency`**, **`Formatting`**, **`GeoMath`** — small stateless helpers. `Extensions/SwiftUI/SwiftUIBackports.swift` holds iOS 18 fallbacks for iOS 26 APIs.

### UI
The app follows **MV (Model–View), not MVVM** — there are no ViewModel layers. Views read `@Observable` models/services directly; per-screen UI state lives in an `@Observable` **screen-state model** (e.g. `MapState`, which does buffered annotation loading, long-press "поеду сюда" points, and heading-follow mode), which owns screen state but does not format data for the view. `RootView` gates onboarding → `MapScreen`, and drives foreground/background GPS mode from `scenePhase`. Features are organized by folder under `Features/` (Map, Search, Trip, Settings, Onboarding).

**No speedometer screen.** The full-screen `DashboardView` («Спидометр») was removed on 11 Oct 2026 at the owner's request («не нужен»), together with its auto-open on trip start, its settings toggle and its GPS boost; the road sketch (`SketchState`/`RoadSketchView`) followed the same day, CarPlay included («не актуально, там ничего не работает»). Panel-aware map insets that used to live in `SketchState` are now `MapFrameState` — the map reports its own height (the sketch view used to, and after it left the insets silently stayed zero). The same day the Apple base map left too: `MapBase`, `mapTraffic`, `CarPlayMapView`, `AppleUserCursor` are gone, and what used to need MapKit on the main screen — the long-press point, the add-camera crosshair (`MapState.center(on:)` → `centerCommand`), the destination flag and the tripod zones — is drawn by the engine (`marks`/`hotspots` sources, `onLongPress`/`onRegion` callbacks). **Camera markers are variant B «Спокойная карта»** (owner's choice, 12 Oct; `Models/CameraMarkerLook.swift`, `CameraMarkerLookTests`): colour means «on our path», not «which type» — a camera ahead on the route (or, without a route, the HUD's nearest camera) is a disc of its type colour, the alert one is bigger with a halo, every other camera is a smaller graphite disc (light graphite with a dark ring at night) whose type is read by its glyph; none ever disappears. `symbol-sort-key` comes from the tier, alert highest — with allow-overlap the higher key lies on top (until 12 Oct the alert had 0 and hid under its neighbours). Badges — «?» for an unconfirmed driver report, a green check for the driver's own camera (not while alerting) — are a separate `camera-badges` layer out of placement. Camera icons are `icon-allow-overlap` **true** — a street label must never push a camera off the map (a radar used to vanish on zoom-in) — and since 12 Oct `icon-ignore-placement` **false**: the camera occupies its spot and traffic lights, labels and POIs avoid it instead of lying on top («задевает иконки камеры»). Traffic lights are a minimal graphite capsule with three light dots (`EngineMapView.trafficLightIcon`, the same shape in `server/omt/make_arrows.py`), drawn under the app's own image name (`EngineModernStyle.ownTrafficLight` → `radar-traffic-light`) because the release sprite, arriving after the style, would overwrite a replaced `traffic-light`. Its slot in the bottom action bar (and in the trip «…» menu) is now **«Мои места»** (`Features/Search/MyPlacesSheet.swift`): Дом/Работа — tap builds the route via the same `buildRoute` as search, an empty slot shows the learned place as a suggestion — plus recent destinations. Every place is set two ways, by address search (`SearchView(initialAssign:)`) or **on the map** (`PlacePickerMap`: a fixed centre pin over **our engine map** since 20 Oct (`EngineMapView` with `lookAt` — the camera opens on the place while the «я» arrow stays at the real position, `showsPosition` hides it when the position is unknown, `onGesture` lifts the pin on every gesture step; an Apple `Map` only in a build without MapLibre), the caption from our own offline `AddressBook.nearest` first and `CLGeocoder` only as a fallback); Settings → Мои места uses the same `PlaceAssignMenu`, and the search's assign banner offers the picker too. A tap on the speed HUD now opens the quick toggles (long-press does the same).

**The main screen learns instead of asking.** The two Дом/Работа circles are gone — empty they read as a chore the app handed the user, while the routine is already on disk. `Models/FrequentPlaces.swift` (pure, `FrequentPlacesTests`) clusters trip endpoints (150 m) and classifies by **routine, not frequency** — home is where you arrive in the evening and leave in the morning, work is where you arrive on a weekday morning; the shop next door is visited more often than work and must never win. Confidence counts *distinct days*, and home is excluded from the work candidates (a morning departure from home and a morning arrival at work look identical). `DestinationSuggestionBar` renders one row — «Домой» / «На работу» — and only when the guess is confident; standing at the place, no guess, or the setting off means no element at all. ### Trip domain & «Итоги» (post-trip summary)
Trip analytics live in `Models/`, not in views (ARCHITECTURE.md rule "data in the model"): `TripRecord` (one saved trip, including its `stops: [TripStop]` and the derived moving/stopped split), `TripHistory` (rolling history), `TripStats` (aggregates + track simplification), `DrivingScore` — which also holds `FineSchedule` (Uzbekistan overspeed fines in BRV), `LifetimeStats`, and `Achievement` — plus two newer pure engines:

- **`TripMerge`** — "same trip or a new one?" after a stop. CoreMotion auto-start dies on any sustained stop, so a supermarket run home used to split into three trips and poison the averages. The decision is not one timer: a **manual** trip end is intent and is never overridden, and *where* you stopped matters — an hour at a random place along the way continues the trip, the same twenty minutes at home means you arrived. Paired with `TripStartMode` (`auto`/`smart`/`manual`) in settings and `TripStopsSection` in the UI.
- **`ArrivalFinish`** — reaching the route destination ends the trip by itself (21.10: «Вы на месте!» sat for six minutes until the owner pressed «Завершить поездку»; arrival only cleared the route, and CoreMotion's auto-stop never fires while the driver sits in the idling car — every `automotive + stationary` sample resets it). After `RouteService.onArrived`, `LocationService+Arrival` watches: parked within `arrivalAutoFinishRadiusMeters` of the destination or the arrival point for `arrivalAutoFinishSeconds`, or CarPlay disconnected there (engine off) → `endTrip(auto: true, atDestination: true)`; never while moving, after a new route, far away, or in «Ручной» (nothing would restart the recording). A recheck timer covers the fix-less standstill. It is an **auto** end (a wrong one — waiting for a passenger — is undone by the short-stop merge), but the record carries `endedAtDestination`, and `TripMerge` weighs the destination like Дом/Работа in the grey zone. `MotionService.rearmAfterArrival` then requires real movement for the next auto-start, otherwise the next «in car, stationary» sample would reopen the trip on the spot. `ArrivalFinishTests`.
- **`PeriodSummary`** / `StatsPeriod` (week / month / all time) — the period report, including the delta against the previous period. Time is always passed in as a parameter, never read from `Date.now` inside the computation, so it is reproducible in tests.

- **`RatingBreakdown`** — the audit trail of the rating. Because the period rating is a distance-weighted mean, each trip's share of the shortfall is exactly `wᵢ(100 − sᵢ)/Σw`, so the breakdown **sums to `100 − R` and can be checked by addition** (a test does exactly that). On top of that: `sources` re-splits the same shortfall by *camera* (a trip's contribution divided by its own penalty ladder, cap included — «Юнусабад, 4 проезда, −18» is actionable where twelve trip rows are not), `baseline` gives the median and usual range over previous windows, and `ratingIfClean`/`tripScoreIfClean` answer "what if I'd driven that camera at the limit" by the same ladder. All of it is assembled off-main by one `@concurrent screen(...)`.

`DrivingScore.breakdown(passed:trackSpeeds:score:)` takes the record's stored score and derives the smoothness line as the remainder: the score is computed at trip end on the *raw* track, but the record keeps the simplified one (≤400 points), whose larger point-to-point jumps doubled the smoothness penalty — the detail screen showed «90» next to a lone «−20». The card now prints the check «100 − 10 = 90», only when it adds up.

All the math is `nonisolated static` and unit-tested (`DrivingScoreTests`, `TripMergeTests`, `PeriodSummaryTests`, `PeriodMapTests`, `TripTrackTests`, `RatingBreakdownTests`). `TripDay.swift` also hosts two smaller tested engines: **`RatingTrend`** (weekly rating series from the day rollups — half-open week windows on purpose: `DateInterval.contains` includes the end, and a Monday trip would count in two weeks) and **`MonthGrid`** (calendar layout for the month view), plus `TripHistory.pendingFineNudge` (stale pending fines older than `finePendingNudgeDays`, with the oldest date so the nudge opens the right period). The «Итоги» screens under `Features/Trip/` (`TripStatsSheet`, `TripStatsCards`, `TripDetailSheet`, `TripHistorySection`, `TripStopsSection`, `SpeedProfileChart`, `PassMapSheet`, `PeriodMapSheet`, `PeriodShareCard`, `StatsInfoSheets`, `AllTripsSheet`, `FinesSheet`, `MonthCalendarCard` — the month-as-cells card, tap opens that day, and `TripEndCard` — the «Поездка сохранена» overlay MapScreen shows right after a foreground trip end, with inline merge suggestion) render a driving rating, real fines-based savings ("штрафы за 30 дней"), streaks, per-camera pass speeds, an overspeed-frequency map, and shareable cards. `ReviewPromptModifier` drives the App Store review prompt.

**History is stored by month** (15.1, `Models/TripStore.swift`, `TripStoreTests`): `Documents/trips/<yyyy-MM>.json` — the month is UTC, because a record's file must not move with the phone's time zone — plus `trips/index.json` (per month: count, records with a track, newest/oldest, byte size). Month files are the truth; the index is a cache, trusted only while the file size matches (a crash between the month and the index makes the month re-read, never lost). Launch reads the months touched by the last `AppConfig.tripHistoryLaunchDays` (62) days and goes deeper only until `keepLast` trips are actually in memory; the rest is `TripStats.olderMonths`, read on demand off-main through the `JSONFile` queue (`loadOlderMonth` — the archive's scroll; `loadAllMonths` — backup, restore, export). `TripStats.written` mirrors what is on disk for every month held in memory: `persist()` writes only the months whose records differ (`TripRecord` is `Equatable` for this), then the index, in one step of the queue, and never writes a month it has not read — `adoptMonths` reads it first (a restored snapshot of an old trip, a split leg past midnight on the 1st). Retention is a parameter, `TripHistory.Retention` (`current` since 27.F: own trips kept forever — no age limit, no record cap — only the simplified track is cut after 7 days because the 62-day launch window would otherwise parse it; `legacy` keeps the old 30 days / 50 records for the pruning-mechanics tests; 15.2 may still turn it into a setting); `pruned(offset:)` makes month-by-month pruning equal to pruning everything, so unread months are swept by the same rule (`sweepOlderMonths`, whole-month deletes decided from the index). `trips.json` is migrated once inside the launch read: months written atomically, then the index, then every month re-read and checked by id, and only then the old file removed — a crash at any step leaves it intact and a re-run is a union by id (the old file wins a conflict). ### Дорога на работу и пробки (12 Oct 2026, `docs/plan_commute_traffic_2026-10-11.md`)

**Commute is computed on the phone only** (`Models/Commute.swift`, `CommuteTests`): home↔work trips by *both* ends (≤ 400 m, manual places outrank learned), travel time without merged-trip stops (`movingDuration`), «обычно» = median over 30 days (≥ 3 trips), the delay of the last trip, and a best departure window (15-min buckets, ≥ 2 trips, ±90 min of the usual departure, ≥ 5 min saving). `TripRecord.startLat/startLon` exists because the track is pruned after a week while the commute needs a month; old records chain the start from the previous trip's end after a normal stop. «Итоги» shows `CommuteCard`s above the period (order by time of day) with a detail sheet (departure → duration chart); the suggestion bar says «Домой · обычно 39 мин». The departure time from home is the most personal datum the app has — it never goes to the server.

**The arrival forecast without a route — the «ghost» (`CommuteGhost`, `CommuteLiveSession`, `CommuteLiveService`) — is calibrated and measured** (stage 24, the owner's «дал 8:25, приехал 8:38»). Both suspected misses were confirmed on synthetic histories (`CommuteCalibrationTests`, 12 km, 15 traffic lights, rush growing 7:30→8:30): the sum of per-segment medians was ~3 min more optimistic than the median of whole trips (each segment is «usually green», each trip has reds), and the ±60/±120 tiers gave 7:40 and 8:20 the same forecast while the truth differed by 5 min. Now (`Models/CommuteCalibration.swift`) rows are weighted by a ~20-min Gaussian kernel on the departure plus a weighted departure slope inside it (the kernel alone dragged the edges of the rush hour to its middle, ~70 s → ~40 s; fallback to the tiers below a mass of 3; the same weekday takes ⅔ of the weight when it has 3+ nearby trips), and the base is scaled to the median of «row / sum of the same segments' medians» (0.9–1.4) — before the limit floor, so it never undercuts the limit; `CommuteLoss` keeps the uncalibrated per-segment base. Every ghost-led commute leaves a phone-only journal entry (`Models/CommuteAccuracy.swift`, `Commute/accuracy.json` next to the profile, outside backups, wiped by «Удалить всю историю», exported as `commute_forecast.csv`): what was said first (~300 m), after 1.5 km, at mid-line, and the real arrival at the end of the line; a trip with a stop or that left the line is not a forecast error. From it: «прогноз ошибался в среднем на N мин» in the commute detail (5+ trips, `CommuteAccuracyCard`, DEBUG `-demoCommutes -demoForecastLog -showCommute`) and a slow residual-bias factor (median of the last 10, half-gain, 0.92–1.12, learned from the *uncorrected* error so it cannot ratchet). Live: the forecast shows from 300 m with an honest «± N мин» when the line was joined at its start (the «other road» gate unchanged, voice still from 1.5 km), a segment we are stuck in enters the pace before its boundary is crossed, crowd jams count above 1.25× one's own median (not q75; the same threshold before departure and for «Моя дорога»), and an arrival shift of 5+ min against what was last said is spoken once per trip — «Прибытие сдвинулось: около 8:38, пробка впереди» — under the same «camera busy» rule as road events (`isCameraBusyForRoadNotes`; DEBUG `-demoGhost shift|early`).

**Traffic is computed on the server from anonymous pieces** — the split is deliberate and mirrors the commute rule. The phone (`TrafficProbes`, `TrafficService`) sends ~1 km pieces (`[[lat, lon, t, kmh]]`, `t` = seconds from the piece start; no device, trip or wall clock; length jitters ±20 % so neighbours cannot be re-chained); the first and last 400 m of every trip are held back and dropped at the finish, nothing within 300 m of home/work leaves, a jump or a 2-min gap breaks the piece. `server/api.py` `POST /api/traffic` stores only those four numbers (IP feeds only the in-memory daily cap) in its own `traffic.db`; `server/traffic_build.py` (cron every 2 min) runs our OSRM `match` (`127.0.0.1:8092`, node-level annotations verified against prod: interior geometry points are the OSM nodes), assigns the observed speed of each leg to its OSM edges `(u, v)`, deletes the raw piece at once, publishes an edge only with ≥ 2 independent pieces in 15 min, levels against the car.lua graph speed (no cold start for "free speed"), accumulates an hour-of-week profile, and writes `/radarmap/traffic/now.json` (`[[ulat, ulon, vlat, vlon, level, kmh, model_kmh]]`, nginx `no-cache`). The app reads it with ETag every 2 min while someone looks (phone scene, CarPlay or a trip), decodes off-main, treats a file older than 10 min as no data, draws a `traffic` layer above the route and narrower (each direction offset to its right — right-hand traffic), and adds to route ETA only slow edges matched by place (≤ 18 m) **and** direction (≤ 35°) (`TrafficSnapshot.delay`); «Быстрый» compares times with traffic. Display-only data — like crowd markers it is unsigned and never touches camera alerts (rule 20); kill switches: Settings («Пробки», «Помогать с пробками») and the pult (`features.traffic`). The `traffic/typical/<wd|off>-<HH>.json` files (8.8.16, «обычно ~N мин (по водителям)» until the driver has 3 own commute trips) age: forward decay with a 5-week half-life, the ≥ 5-piece threshold counts decayed pieces, the «two cars in one 15-min window» mark expires after the same half-life, weekday holidays go to `off`, and only a piece that passed an edge end to end (25 m from the match ends) is a witness — two adjacent pieces of one car used to vouch for each other. Next step (not done): OSRM on MLD + `osrm-customize` fed from the same edges — the server's graph rebuild does not fit in memory today, see `crontab.txt`.

Since 10 Oct 2026 the map in the car is **our MapLibre engine** (`CarPlayEngineLayer` → the same `EngineMapView` as the phone), the only map there since 11 Oct 2026 (the MapKit fallback and the «Схема» mode are gone). Buttons: bar — trip ▶/■ and sound on the leading side, «Куда» (magnifier, in both states) and «Радар!» trailing; «Радар!» is a **text** `CPBarButton` («Radar!» in Uzbek, 21.10, 25.H3) — the `dot.radiowaves` glyph alone read as AirPlay/«вещание» in the car. Bar glyphs are bare (`play.fill`, `stop.fill`, the sound symbol, `magnifyingglass`) and the same as on the phone: the system draws the glass capsule, and a symbol with its own circle/diamond/bubble inside it read as heavy blots (owner, 12 Oct). **Map buttons by state — `CarPlayMapButtons`** (pure, `CarPlayMapButtonsTests`): without a trip +, −, panning (four arrows, as in Apple Maps), «к себе»; **in a trip «Радар!» comes first** — a rendered yellow disc with the word (`CarPlayReportImage`, 40 pt, `alwaysOriginal`, its own inverted `focusedImage`: a system-made one is the alpha silhouette, a solid circle) — then +, −, and panning and «к себе» share the fourth slot by follow state (following: «к себе» is a no-op, so panning; detached: «к себе», after which panning is one tap again); in panning exactly ±; on the route preview the no-trip set. Both «Радар!» call `quickRadar`, ReportGuard inside. Whether a head unit keeps the disc's colours and scales a 40 pt image is 🚗. **Phone and car are in one route phase — `Models/NavigationFlow.swift`** (`NavigationFlowTests`): no route = free; route without a trip = *choosing* (phone: RoutePanel «Поехали»; car: the `CPTrip` preview with the same button — a route built on the phone, left by an auto-stop, or waiting when the car connects opens it, «Поехали»/✕ on the phone closes it); route + trip = *guiding* — the only phase in which `CarPlayGuidance` runs a session. A **manual** trip end (any screen, Siri) clears the route; an auto-stop and «я пассажир» keep it. Before this, «Стоп» in the car said «Поездка завершена» while the maneuver card and ETA stayed, and the car kept guiding under the phone's «Поехали». Car choice decisions are taken on phase *transitions* and never while `RouteService.isBuilding` (the in-between phase of a build would otherwise break «drive at once» on the move). Panning follows the `CPMapTemplate` contract: the system draws no exit, so while the panning interface is up the bar holds a single «Готово» and only the two zoom buttons stay (the system shows at most two). **The idle return (`carPlayFollowReturnSeconds`, armed from the moment panning opens) and a camera ahead close the panning interface too** — one pure decision, `CarPlayBrowse` (`CarPlayBrowseTests`), executed by `CarPlayMapModel`; until 18.10 they recentred the map but left the bar as a lone «Готово», and an untouched panning interface had no timer at all — the owner's «нет кнопок, где функционал». A dismissal the system does not confirm within `carPlayPanningDismissFallbackSeconds` restores the bar anyway. Buttons are built *before* `setRootTemplate` (set without animation — an animated root set on a backgrounded scene is lost), and re-sent past the `sentBar` cache on panning dismiss, in `templateDidAppear` and in `sceneDidBecomeActive` — a bar sent before the template is on screen simply vanishes on the head unit (2.2.1/2.2.3 in CarPlay Simulator). The permission alert and «куда едем?» wait until the root is on screen, never the `setRootTemplate` completion (it fires in 25 ms while the host still holds the scene in the background). The navigation session no longer waits (20.10, scenario D1): a car that connected while showing Home or Yandex got no session at all until the driver opened RadarMap — no dashboard maneuver, no camera banners over the other app — so guidance attaches after `carPlayRootSettleDelay` once the system confirms the root set, and the first on-screen showing restarts that background session once (`CarPlayGuidance.restartSession`). «On screen» is the root's `templateDidAppear` **or** an active scene whose root set the system confirmed, after `carPlayRootSettleDelay` — the system does not always send `templateDidAppear` for the root (logs of 12 Oct, carplay4/carplay10: a car that connected while the scene was off screen never got it, so the session never started and the old watchdog re-set the root 3 s after every return to the app). The decision is `CarPlayRootWatch` (pure, `CarPlayRootWatchTests`): a confirmed root is never set again, an unconfirmed one once per connection after `carPlayTemplateShowTimeout`. `mapTemplateDidCancelNavigation` means another navigator (or the car's own) took guidance, and RadarMap **yields completely**: the route is cleared, the trip and camera alerts stay (the Yandex-companion case), and guidance comes back only with a new route the driver asks for (20.10, scenario D1). Until then the route lived on: the phone spoke its turns over the other app's, rerouted along the other app's line, and merely opening RadarMap to tap «Радар!» took guidance back from Yandex (the 2.2.16 `refresh(driverReturned:)` retake, removed). The same `refresh` re-sends the last maneuver and estimates whenever the driver leaves our screen or the dashboard appears, and the session never drops to zero upcoming maneuvers while a route is active (an empty list reads as «not navigating»). «Поездка» in the bar ignores a second tap within `carPlayTripToggleGuard` (2 s) and answers with a banner — carplay12 showed start-then-end 0.6–0.9 s apart twice: the icon change reaches the head unit late, the driver tapped again, and a parked second tap ends the trip without asking. The dashboard tile keeps the nearest camera in frame (`DriveCamera` `keepAhead`, ≤ 500 m) and its gauge shows that camera (the rule the main dock used before 21.10) plus remaining time and arrival when routing; its Дом/Работа buttons speak when no route can be built. Pinch (iOS 26) is read as scale-since-gesture-start and reset per gesture (`mapTemplateDidBeginZoomGesture`). **Route choice in the car** (`CarPlayTripPreview`): after «Куда» parked, a CarPlay trip preview with 2–3 variants, our labels, traffic-aware time and its colour (no data → system colour, never «green»), «Отмена» alone in the bar and the navigation session only after «Поехали»; moving → no preview, moving off during it → accepted. **«Куда едем?»** — a banner once per connection, parked, no route. **Trip summary** one line after saving. **Rerouting** pauses guidance with `.rerouting` and the next maneuver resumes it. **No junction sketch** (21.10, the owner: «мини-карту убери, там лучше — с какого края нужно повернуть»): the rough schematic of the node in the maneuver card (`JunctionSketch`, `junctionImage`) is gone; that space holds the lane row when OSRM knows the lanes, otherwise the lane side rides in the instruction text («Поверните налево на улицу Лабзак, левый ряд», `LaneAdvice.instruction`). The card itself is `CarPlayGuidance.card(for:carDark:metadata:)` — pure, tested. **Navigation metadata** fields are all set (junction type, exit angle, maneuver state); whether they are sent is the setting «Манёвры на приборке и HUD» (below). «Куда» shows «АЗС», «Зарядка» or both by Settings → Поездка → «Машина» (`VehicleEnergy`); the keyboard «Найти» in CPSearchTemplate pushes the full result list (it did nothing); grid icons are fitted to `CPGridTemplate.maximumGridButtonImageSize` (40×40 — a 36 pt symbol came out 52×44). **The car window has ONE permanent root for the whole connection — `CarPlayWindowRoot`, set as `window.rootViewController` in `didConnect`, exactly as Apple's sample does — and only its content (the SwiftUI host) is swapped** (2.2.7). Both CarPlay window bugs of 11 Oct were about that root, per the `CarPlayTemplateUIHost` logs: 2.2.5's watchdog replaced `rootViewController`, and the head unit kept presenting the old root's layer (frozen frame, live buttons); 2.2.6 set the root only later in `sceneWillEnterForeground`, and the host logged «Removing visibility view for pid …, not considered visible» / «Not installing presentation view» — a blank car screen with no map and no bar. The window content (and so the `MLNMapView`) is created only when the app is not in the background — MapLibre 6.29 starts a map created during `applicationState == .background` dormant and does not always wake it — otherwise in `sceneDidBecomeActive`. The watchdog repairs only on GPS-tick lag; its `TimelineView` heartbeat is a log-only clue (a clock not taken from the car screen stops while the phone display is off). **Navigation metadata for the cluster/HUD is a setting, OFF by default** (26.4, 21.10: Settings → Маршрут → CarPlay → «Манёвры на приборке и HUD», `AppSettings.carPlayNavigationMetadata`, default `AppConfig.carPlayNavigationMetadata` = false — the owner checks it in his BYD). The system asks `mapTemplateShouldProvideNavigationMetadata` **only inside `startNavigationSession`** (disassembly of CarPlay.framework, iOS 26.2: the single call site is `-[CPMapTemplate startNavigationSessionForTrip:]`, which feeds `setSendsNavigationMetadata:` of the session and the trip), so `CarPlayGuidance` snapshots the setting right before that call (`sessionMetadata`, which the delegate returns and the card and maneuver state read — never the live setting), and a toggle during live guidance starts the session anew (`metadataNeedsNewSession`) — it takes effect at once, with one card reload in the car. The log says the value at connect, the system's question and each session start. Turned on in 2.2.4 without junction type and maneuver state, it was blamed for a maneuver card with only a distance — but Apple's guide says metadata only adds to the symbol and text, and that card had no arrow because `CarPlayGuidance.symbol` returned nil until 2.2.15 (audit 18.10). All fields are set now and every maneuver is `add`ed first; turning it on needs one check on a cluster display (CarPlay Simulator in Xcode 27 Device Hub), and the lane row must then stay off (it is). Touch-drag panning reaches only the `…PanGesture` delegate callbacks, only on cars that support it — verify in a car; the delegate logs «перетаскивание пальцем». Every stock CarPlay Simulator preset is `primaryInput: Touchpad`, and there a mouse drag reaches the template host as focus presses (UIEvent types 3/5 to `CPSWindow`, carplay10), never as touches; a Touch-primary copy is `~/Library/CarPlaySimulator/UserConfigs/Widescreen Touch.yaml` («Widescreen Touch (RadarMap)»), and the simulator reads configs only at launch (Apple forum 730949 reports no drag even so). Research, sources and measurements: `docs/carplay_research_2026-10-11.md`. **The window content is built only while the scene is on screen, and rebuilt fresh on every return** (2.2.6). The «window frozen, buttons alive» bug was reproduced on 11 Oct under a device log (CarPlay Simulator, phone on the desk): the scene connected in the background (a trip running on the phone, Yandex last on the car screen — FrontBoard `BG-Active`, Core Animation «cannot add handler to 0 from 0»), the old `activationState != .background` check let it build the map and HUD anyway, the GPS-tick watchdog then recreated the host — still in the background — and when the driver opened RadarMap the template buttons worked while the window never repainted. Now `isOnScreen` defaults to false and is true only for `.foregroundActive/.foregroundInactive`; `installHost` runs at connect only if on screen and otherwise in `sceneWillEnterForeground`, always fresh after any background period (`needsFreshHost`); the dashboard scene follows the same rules (it used to mount a second engine in a background tile). The watchdog acts only in `.foregroundActive` and has two clues written by the tree itself (`CarPlayLiveness`): the GPS tick and a 2 s `TimelineView` heartbeat — the tick alone is blind on a parked car (no fixes for minutes), which is exactly how the desk repro slipped past it; at most `carPlayFreezeRepairs` rebuilds per showing. `RouteService.apply` computes the first maneuver at `along = 0` immediately (a parked car showed «Loading…» on the car until the next fix), and distances go to CarPlay in a unit the system prints short: the maneuver card in metres below 1 km (`CarPlayGuidanceMapping.distance`, printed medium-style — «120 m»), the trip ETA bar and route previews **always in kilometres** (`tripDistance`, «0,8 km»): CarPlaySupport prints that bar's unit with `MeasurementFormatter.string(from: unit)` in *short* style and the phone's own locale, which for metres is a word — «12,834 meter» (11.10), «780 meter» under a «120 m» card (drive 21.10), «metr» in Uzbek. The dashboard tile on the CarPlay home screen (`CarPlayDashboardSceneDelegate`) exists only if `CPSupportsDashboardNavigationScene` sits **inside** `UIApplicationSceneManifest` — from 10 Oct to 2.2.4 it sat one level up, the system ignored it, and RadarMap never reached the CarPlay home screen while Yandex/Amap did; verify with `plutil -extract UIApplicationSceneManifest.CPSupportsDashboardNavigationScene raw -o - <built>/RadarMap.app/Info.plist`. Position comes only from `LocationService` — the MapKit view used to run its own GPS, so the marker moved while our speed/alerts pipeline stood still (the owner's «it moves, but km/h and the buttons are dead» report). There are no touches in the CarPlay window: pan, ±, «к себе» arrive from `CPMapTemplateDelegate` as commands on `CarPlayMapModel` (`panCommand`, `zoomBias`/`zoomCommand`, `recenter`); the drag translation arrives as a **per-frame increment**, not from the gesture start (measured 12 Oct, carplay11: 135 calls of −10…−40 pt in one 2.4 s drag, the last ≈ 0) — until 2.2.15 it was read as cumulative and differenced, which left only noise and the map did not move. Template buttons are re-sent only when their state key changes — every send replaces them on the head unit and a tap during the swap is lost. Day/night is one value (`model.isDaylight`) for the map AND the HUD (`colorScheme` on the host): manual setting first, then the car's `contentStyle`, then the sun. `CarPlayGuidance` runs a real `CPNavigationSession` (maneuver card, estimates, `pauseTrip(.loading)` until the first maneuver); our own maneuver banner hides while it runs. **Lanes on the car screen are a second, text-less maneuver** — `CarPlayGuidance.laneRow`, a ≤ 120×18 pt image shown `.symbolOnly` via `mapTemplate(_:displayStyleFor:)` (Developer Guide p. 48), still with one instruction variant (the header demands at least one; until 21.10 it went with an empty list, and the owner never saw lanes in the car); `CPLaneGuidance` feeds only the cluster metadata, which is off, so before 18.10 the car had no lanes anywhere. With metadata on the row is not sent (the cluster would read it as a second turn). **Every banner over the car map goes through one queue — `CarPlayBanners`** (`CarPlayBannerPolicy`, `CarPlayBannerPolicyTests`): CarPlay shows one `CPNavigationAlert` at a time and silently drops a new one; priority camera > detour > «радар ещё на месте?» > «куда едем?» > confirmations; a displaced detour or question comes back when the screen frees (`onIdle`), a late confirmation is dropped. **The camera ahead is a system banner on our screen too** (`CarPlayCameraBanner`, since 18.10; before, our screen had only the dock pill): on our screen it stays for the whole approach with the distance counting down (`updateTitleVariants`, ≤ 1/s), over another app it is the old `carPlayCameraAlertSeconds` notification. **The dock holds only speed + limit** (21.10, `Models/CarPlayCameraCue.swift`, `CarPlayCameraCueTests`): the Developer Guide (pp. 7, 36) does not want app panels over the map in the base view, and Waze/Google Maps pass review with exactly a speed+limit corner; so the camera left the dock — the camera ahead is the system banner (any alert level ≥ 1 at ≥ `directionalMinSpeedKmh`, i.e. `isApproachingCamera`), a «400 м» label next to its icon on the map (`camera-label` source, one point, rewritten ≤ 1/s) and, on iOS 27, a `CPRouteDetail` «📷 400 м» in the trip estimates. A **familiar** camera (voice muted) gets none of these and no alert look on the map — only its icon with the green check. The phone HUD is untouched; «Нет сигнала GPS» moved from the dock to `CarPlayStatusChips`. **iOS 27 surfaces** (25.H1, 21.10; all behind `#available(iOS 27)`, iOS 18–26 unchanged — `.locating` and attributed text are older APIs gated by the plan): the camera banner carries `avatarImage` (the type disc in its marker colour) and `alertImage` (the limit sign — or the type when the limit is unknown — plus the phone's proximity bar in `carPlayBannerProximitySteps` steps; `CarPlayCameraBannerLook`, drawn by `CarPlayBannerArt`), redrawn with the distance only on a new step/sign/theme, with no close button («Понятно» closes); the «Радар!» refine is one banner with `actions` «Тренога / Пост / ДТП» (+ «Отменить» if `maximumActionsCount` leaves room), still through the queue as `.request`; close or silence keeps «радар», and fewer buttons than kinds falls back to «Тренога / Другое» + grid (`CarPlayRefineChoice`); `CPNavigationSession.optionsPanel` — the «…» of the ETA card (`CarPlayOptionsPanel`, `CarPlayOptionsPanelContent`): up to 5 cameras ahead on the route, a sound toggle (silence ↔ what it was before in this car), «Завершить маршрут» as the primary button (route only; trip and alerts stay), rewritten ≤ every 3 s while open and only on a change of composition while closed; `pauseTrip(.locating)` while `isSignalStale` once a maneuver was shown (rerouting outranks it), lifted on the first accepted fix by re-sending the maneuver, and the «Нет сигнала GPS» chip yields to that card (`CarPlayGuidancePause`); the maneuver text ends with a 25×25 limit-sign attachment only when two probes 50/120 m past the turn agree on a limit that differs from the one 40 m before it (else the current one) — `CarPlayManeuverLimit`. All pure decisions are tested; the system image limits and button count are runtime-only (logged once per connection), so their look on 800×480, the panel, and whether a `CPListItem` handler fires inside a `CPMapPanelItem` are 🚗 (no iOS 27 simulator runtime here). Arrival or the commute ghost pill stays beside the speed only while the car draws no estimates of its own. Confirmations («Поездка началась», trip summary, the «Радар!» outcome) and «радар ещё на месте?» are banners, not full-screen `CPAlertTemplate`s (the question only below `carPlayQuestionMaxKmh`; closing it unanswered = «Пропустить»); a modal alert remains only for an error answering the driver's own tap. Maneuver and camera symbols are **rendered bitmaps** of one colour chosen for the known background (`CarPlayGuidance.symbol`, tested): until 2.2.15 they were built as a fresh `UIImageAsset` of two symbol variants, `asset.image(with:)` returned nil, and no arrow ever reached the car (carplay11: «стрелка false»). «Куда» has a search tile (`CPSearchTemplate`, own `AddressBook` first, Apple second), disabled with «Поиск на стоянке» while the car limits the keyboard (`CPSessionConfiguration.limitedUserInterfaces`, rebuilt live via `updateGridButtons`); an unset Дом/Работа tile assigns the place right there by search (every flow must work without the phone, Developer Guide p. 5); lists are capped at `CPListTemplate.maximumItemCount`. Session hitches/minutes go to `UsageStats.carPlay`; in release `HitchWatch` starts with the car scene and stops on disconnect (it used to ping main every 0.5 s until the process died). CarPlay without a trip runs the same GPS accuracy ladder as a trip (`tuneAdaptiveAccuracy`), not a constant Best/5 m — but **while a map is watched (CarPlay connected or the phone open) the ladder changes accuracy only, never the distance filter** (`GPSTiers.request(tier:watched:)`, 12 Oct): the cruise filter of 25 m gave one fix per 2–3 s at 40 km/h and the standstill 30 m kept «0 км/ч» for thirty metres after moving off — the owner's «спидометр не успевает, карта рывками». In the pocket the battery ladder is unchanged. The follow camera animates for the real interval since the previous fix (cap `engineCameraDuration` 1.25 s), not 0.8 s and then a standstill. **On the move the map shows only the road** (`DrivingDeclutter`, hysteresis: hide from 12 km/h, show after 4 s below 4 km/h): pedestrian underpasses and footpaths (the wide purple bands across avenues — «убери тоннели»), tunnel overlays, trees and shadows, parking marks, POI icons and asphalt grain are hidden by layer visibility (`EngineMapView.drivingHiddenLayers`), roads, lanes, zebras, signals, fuel, route and cameras stay; CarPlay always, the phone during a trip. The dashboard tile is `interactive: false` (a stray gesture used to stop following for good — the tile has no «к себе»). Both car maps log a **health line every 10 s** (`healthTag` «машина»/«плитка», `Log.carplay`): app and scene state, whether the window is on the phone's screen, MapLibre's dormant flag and display-link state (KVC on 6.29 internals, guarded by `responds(to:)`), frames rendered, applies, camera moves, browsing, map direction vs course, zoom, cameras in the source and in view — the dashboard tile lagged, did not rotate and showed no cameras on 12 Oct, and the simulator has no dashboard, so a device log is the only witness. Plan and the analysis behind it: `docs/plan_carplay_drive_2026-10-10.md`. The phone scene and CarPlay share one composition root via `AppEnvironment.shared` (CarPlay can connect before the SwiftUI scene comes up). `RadarWatch/` (`RadarWatchApp`, `WatchHUDView`, `WatchSession`) is a watchOS companion showing the trip HUD with escalating wrist haptics, fed by `WatchBridgeService` over `WatchConnectivity`. **The «следующая камера» complication** (`RadarWatchWidgets/`, 9.3б; circular, rectangular, corner, inline) is fed by the watch app, not the phone: `ComplicationFeed` turns each received context into a `WatchComplicationSnapshot` in the App Group (the watch has its own `group.uz.radarmap.ios` container) and reloads WidgetKit only by `Shared/WatchComplication.swift` (pure, `WatchComplicationTests`) — trip start/end always, another camera or distance step at most every 2 min and 40 times a day, an unchanged trip refreshed after 8 min. The distance is an **upper bound** («< 1 км»): between reloads the car covers kilometres, and to a camera ahead the distance only shrinks. A trip snapshot older than 10 min is drawn dimmed with «данные на 12:04» — the watch cannot tell a red light from a dead phone. `.backgroundTask(.watchConnectivity)` keeps the sleeping watch app awake until the context is applied. Camera discs are the map marker colours (`WidgetPalette.cameraFill`, checked against `Theme.Types`). **The phone wakes a sleeping watch for the face** (14.5): every context also carries the camera id (`cid` — two cameras at one address are told apart; from an old phone without it the watch falls back to address + icon, and an id appearing mid-trip is not a reload) and the send time `t` (the snapshot is dated by it, so a context that waited an hour reads «данные на …», not fresh). On trip start/end and another camera ahead — never on a distance step or a tick — `WatchComplicationPush` (pure, `WatchComplicationPushTests`) adds `transferCurrentComplicationUserInfo` with the same payload: only with `isComplicationEnabled` and the watch app off screen (`isReachable` false), camera changes no more often than the watch would redraw (2 min, 40/day), and only while `remainingComplicationUserInfoTransfers` stays above `watchComplicationEdgeReserve` (4), so the 50/day budget survives to the trip end; the previous outstanding push is cancelled first. The context always goes as well — no budget means «later», not «never». The watch takes a push only if it is newer than what it applied and not older than 10 min (`WatchComplication.acceptsPush` — userInfo is a queue, the context is not), runs it through the same `ComplicationFeed` (context + push of one state = one reload) and never buzzes from it. Caveat: the API is not deprecated in the iOS 27 SDK, but Apple engineers said on the forums (2024) that it does not yet wake apps whose complications are WidgetKit-based — it then behaves like `transferUserInfo` — and `isComplicationEnabled` is reported false for a Smart Stack-only widget; the supported external wake is a WidgetKit push (`WidgetPushHandler`, watchOS 26+, APNs from a server), not used here: the deployment target is watchOS 11, and the trip state with a camera id is a location that must not go through our server.

**The instrument cluster is a third car surface** (25.H2, 21.10; `CarPlayInstrumentClusterSceneDelegate`, iOS 15.4 `CPTemplateApplicationInstrumentClusterScene`): our map in the cluster window, no buttons and no gestures, always following; zoom comes from the car (`instrumentClusterControllerDidZoomIn/Out` → `CarPlayMapModel.zoom`). The window arrives separately from the scene, via `CPInstrumentClusterControllerDelegate` (and is also read from `instrumentClusterWindow` at connect, in case it came before the delegate), and gets the same permanent `CarPlayWindowRoot` per window; content only while the scene is foreground and the app not in the background, dropped at once on `sceneDidEnterBackground` (the driver switched the cluster to the car's gauges). What differs between the three car maps is one pure value, **`CarPlaySurface`** (`car`/`dashboard`/`cluster`, `CarPlayClusterTests`): the cluster is a *second* simultaneous engine map (the phone map already yields to CarPlay), so it is flat at any temperature, house-less, always decluttered, at `engineHotFPS` (via `covered`), health tag «приборка»; on a `.minimal` thermal phone it is the first map to go (`CarPlayCluster.showsMap`). The car decides the overlays: `speedLimitSetting == .disabled` means the car draws its own sign — ours never appears next to it — otherwise the sign follows «Ограничения скорости»; the compass (blue, never red) only on `.enabled`; speed is never drawn (the speedometer is the car's). `inactiveDescriptionVariants` promise warnings only during a trip. Manifest: `CPSupportsInstrumentClusterNavigationScene` **inside** `UIApplicationSceneManifest` plus the `CPTemplateApplicationInstrumentClusterSceneSessionRoleApplication` configuration; verify with `plutil -extract UIApplicationSceneManifest xml1 -o - <built>/RadarMap.app/Info.plist`. Navigation metadata is OFF by default on purpose (a setting since 26.4): turning it on removes the lane row from the car screen (`CarPlayGuidance.Card.upcoming` is one maneuver then, lanes go only as `CPLaneGuidance`) — the owner's call after the second-display check (`docs/plan_full_2026-10-19.md`, 25.H2).

**Gotcha:** the CarPlay scene is wired by the hand-written `UIApplicationSceneManifest` in `RadarMap/Info.plist` (role `CPTemplateApplicationSceneSessionRoleApplication` → `$(PRODUCT_MODULE_NAME).CarPlaySceneDelegate`). The app target must therefore **not** set `INFOPLIST_KEY_UIApplicationSceneManifest_Generation` (Xcode's "Generate Info.plist scene manifest" checkbox): it replaces the whole key at build time, leaving `UISceneConfigurations` an empty dict, and CarPlay then crashes on connect with `NSGenericException` «Application does not implement CarPlay template application lifecycle methods in its scene delegate» — the delegate is never instantiated. Verify with `plutil -extract UIApplicationSceneManifest xml1 -o - <built>/RadarMap.app/Info.plist`. `CarPlaySceneDelegate` deliberately implements the `toWindow:`/`fromWindow:` variants of the connect/disconnect callbacks — those are the ones for navigation apps, not deprecated leftovers.

### Widgets & sharing
`RadarMapWidgets` (Live Activity in Dynamic Island + home widgets). In CarPlay (iOS 26 shows `systemSmall` widgets on the car home screen) the stats widget is `disfavoredLocations([.carPlay], for: [.systemSmall])` — moved to the gallery's «Other» section, the only placement API WidgetKit has; «Дорога на работу» stays; the Live Activity's car/Smart Stack face is the declared `.small` (`supplementalActivityFamilies`, no buttons). The stats widget's hero is **kilometres**, not the rating: people look at a home screen for the fact, and go to «Итоги» for the verdict. The ring fills toward the driver's **own usual week** (median of the previous eight, `WidgetWeek.median` — a median so one trip to Samarkand doesn't make every later week look like a failure); overshoot is said in words, because a second lap reads as a rendering bug. Seven day bars carry the week's shape, `systemLarge` adds month/lifetime/wheel-time tiles and the week's worst place.
  It renders **four states**, and that is the part that was missing: `noAccess` (App Group not granted by the signature — a personal team can't give it, and «you didn't drive» is the wrong thing to say then), `empty` (no trips — an invitation, never a zero), `few` (1 active day or no norm yet: no ring, no bars, no averages, because there is nothing to compare with — the subtitle names the last trip instead), and `full`. `WidgetWeek` (in `Shared/`, tested by `WidgetSnapshotTests`) holds every one of those decisions plus «is this snapshot even about the current week» — the widget writes nothing and computes nothing, the app fills the snapshot on scene-background and every trip end. DEBUG hook `-widgetState empty|few|full` seeds a state so all of them can be screenshotted without waiting for Monday. Shared code lives in `Shared/`: `CameraActivityAttributes` (Live Activity contract) and `SharedDefaults` (App-Group `UserDefaults` snapshot for the home widget; written by `AppEnvironment.refreshWidgetSnapshot()` on scene-background **and** on every trip end — a background auto-stop must not leave the widget stale; the widget itself never computes or refreshes anything). The write and `reloadAllTimelines` happen only when `WidgetWeek.needsRefresh` says the numbers changed or the snapshot is older than 12 h — an unconditional reload on every background/launch burned WidgetKit's daily budget before the trip end that actually needed it. `group.uz.radarmap.ios` is declared in **all three** entitlements files — app-on-device, app-on-simulator, widget — and matches `SharedDefaults.appGroup`. Keep it that way: with the group missing from any one of them `UserDefaults(suiteName:)` silently returns `nil` and the widget renders a placeholder that looks like a widget bug rather than a signing one. The simulator file carries it on purpose, so the widget can be verified before a device install (`xcrun simctl get_app_container <udid> uz.radarmap.ios group.uz.radarmap.ios` shows the container and the written snapshot). The Live Activity is unaffected either way — it goes through ActivityKit, not the App Group.

**The watch complication is detached from the build (2.2.26, 21.10.2026).** `RadarWatchWidgets` (`uz.radarmap.ios.watch.widgets`) has no App ID in the developer account yet, and Xcode Cloud archives of 2.2.24/2.2.25 failed on signing («Action required»). The target and its code stay in the project; only the «Embed Foundation Extensions» phase (`6FA6F8A88A04E12A7182B3A1`) and the dependency (`6FA6686A8733735191D96FB9`) were removed from `RadarWatch`. To bring it back: open the project in Xcode, `RadarWatchWidgets` → Signing & Capabilities → automatic signing (team RL7M4Z58CJ) so the App ID and App Group get registered, then re-add both lines to the `RadarWatch` target.

## Backend

The VPS itself is provisioned separately (nginx, Docker, cron), but the app-facing backend code now lives in **`server/`** — all Python is stdlib-only:
- `api.py` — the crowdsourcing/metrics/feedback/usage API: `sqlite3` + `http.server`, listens on `127.0.0.1:8091`, exposed by nginx at `:8090/api/`. Mobile-radar reports merge via up/down **votes** (`/api/report`, `/api/vote`) with per-device caps against ID rotation; markers are rate-limited and live a **trust lifecycle**: a new report gets a short probation TTL (radar 75 min) and the full one (3/6 h) only after confirmation by an *independent* driver — different device AND different IP — so a planted fake dies on its own while UUID rotation can't self-extend it; `confirmed` ships in `/api/mobile`, a dislike from a fresh IP cuts 30 min off (full hide still needs the 3-distinct-IP quorum), a same-device different-type re-report within 400 m / 10 min is an **amend** (retype own point, not a second marker), and one IP can hold at most 12 live markers. Schema, migrations and indexes live in `init_db()` and run **once at startup** — they used to run on every HTTP request (six `CREATE TABLE IF NOT EXISTS` and four `ALTER TABLE`, all four always throwing). WAL + `busy_timeout` are mandatory: without them one `POST` during a poll handed readers `database is locked` as an instant 500. `BoundedHTTPServer` caps concurrent handlers at 64 and answers 503 above that. `test_api.py` covers it (129 cases, `TrafficTest`, `EtaShareTest` and `EtaWriteKeyTest` included). **«Поделиться прибытием»** (`POST /api/eta`, `GET /api/eta/<token>`) keeps only the page address, ETA, distance left and status, in process memory (a restart wipes every link — the price of nothing on disk), and expires links itself (2 h without updates, 30 min after the end); the page has no script, `no-store`, `noindex`, ru/uz by `Accept-Language`, `X-Eta-Version: 2`. **Reading and writing are different keys** (14.12): the phone keeps a random write key W and posts `{key: W, token: R, …}`, the link carries R = base64url(sha256(W)), 43 chars; the server stores no secret (the right to write is knowing a preimage of the address), stores under the hash and marks the entry `keyed`. A bare `token` is the pre-14.12 format (22 chars, address and key at once) and is accepted only up to 42 chars — so the reader of a link can never write to it, not even when no entry exists (a family link between trips home, after a restart, after an eviction). `token` next to `key` is for a server older than 14.12, which ignores `key` and writes by `token`: the same request works on both, and the phone never needs to know the server version. Deployed with `deploy_api.sh` (which also ships `admin.py`); `backup_db.sh` takes a daily consistent `reports.db` snapshot via sqlite's `.backup` (not `cp` — the DB is live) and keeps 7; `healthcheck.sh` (cron, every 5 min) watches api/OSRM/`version.json`/disk/backup freshness and reports **only on a state change** — a message every five minutes stops being read by day two.
- `telegram_bot.py` / `test_telegram_bot.py` / `deploy_bot.sh` / `radarmap-bot.service` (12б.7) — reports through Telegram (location → type button → the same `/api/report` / `/api/cng`), long polling, no open ports; the Telegram id is never stored — the device is `scrypt(id · 30-day window, salt)` (N=2^12, r=8: ~7 ms, one per update; with the salt on the same VPS a plain sha256 let a compromise brute-force the ~10^10 id space in an hour and de-anonymise every past report — audit 14.3) and another slice of it goes to the API as `X-Real-IP: tg-…`, so bot users can confirm each other and caps are per person. A methane answer is posted at the nearest CNG venue (kind 12) ≤ 60 m from the published venue files (`venues_dir`, default `/opt/radarmap/www/roads`, coordinate = int ÷ 1e5 exactly as `VenueBook.decode`) so it keys to the phone's station; no venue nearby → refused and not counted, no readable files → methane refused (fail closed, logged once). The bot's interval mirrors the API (120 s between created reports of one category, a retype passes to the API's amend), a 429 reads «Не так часто», and only a 200 counts toward the 15/day. Config `/opt/radarmap/telegram_bot.conf` (token, salt, optional venues_dir, app_url, owner_hash) by the owner. Since 23.x (`docs/plan_bot_2026-10-21.md`) the bot also GIVES: a location → one «что рядом» card (live reports from `/api/mobile`/`/api/road` with honest «не подтверждена», stationary cameras from the webroot `cameras.json` with the moderator's signed `overrides.json` applied exactly as `CameraOverrideEngine` does (23.9: Ed25519 via `status.verify_ed25519`, hide/move/retype, a move > 500 m or outside Uzbekistan dropped, > 5 % hidden rejects the file, any defect means the base as is; thresholds checked against `AppConfig.swift` by `OverridesContractTest`), nearest CNG with `/api/cng` status; 5 km, «дальше — 15 км»; 1 per 20 s), `/metan`, live-location companion (new items ahead every ≥ 60 s, «ещё стоит?» → `/api/vote kind=pass`), `/pereval` with hazard subscriptions, `/city` (confirmed tripods/posts via `telegram_publish.select_confirmed`, quiet 23–07, ≤ 6/h), `/my`, `/stats` (owner by `owner_hash`), cancel own report for 2 min — `bot_texts.py` (ru/uz), `bot_near.py` (pure logic + sources), `bot_subs.py` (bot.db subscriptions, chat id sealed with a salt-derived key, delivered by `family_notify.Courier`), `test_bot_features.py`. The location is never stored or logged; the pult `features.bot=false` turns off everything but reporting. Profile/menu are set by the bot at startup only when changed.
- `build_route_graph.py` / `publish_route_graph.sh` (12б.10) — the offline route graph (see above), signed index `routes/route_graph_index.json`; `registry_diff.py` — read-only registry vs DB report.
- `traffic_build.py` / `test_traffic_build.py` (15 cases, on a recorded prod OSRM `match` response in `fixtures/`) / `deploy_traffic.sh` — the crowd-traffic builder described under «Дорога на работу и пробки»; cron line in `crontab.txt`, nginx `location /radarmap/traffic/` in `nginx-radarmap-location.conf` (installed by hand like the rest of the snippet). Deploy order: `deploy_api.sh` (the ingest endpoint) → nginx → `deploy_traffic.sh`.
- `build_road_weather.py` / `test_build_road_weather.py` (on a hand-recorded open-meteo answer in `fixtures/`) / `deploy_road_weather.sh` — road weather (19.1): the curated points in `road_weather_points.json` (Kamchik on A373 in four points, Takhtakaracha on M39 in three, plain M39/A373 stretches; each carries a «проверить» note for the owner), one open-meteo request for all of them every 30 min, hazards for now + 6 h (snow, ice = t ≤ 0 with precipitation or a freezing code, fog < 200 m visibility, wind ≥ 15 m/s; null is not a hazard), `weather/roads.json` written atomically only on change or hourly (so the phone's 2 h staleness never trips on a healthy server). Open-Meteo is CC BY 4.0 — credited in `ATTRIBUTION.md` and the «О приложении» footer. nginx `location /radarmap/weather/` installed by hand.
- `admin.py` + `admin_auth.py` — the moderation panel: a separate stdlib process on `127.0.0.1:8093`, server-rendered HTML. **Login is a password** (scrypt hash in `/opt/radarmap/admin.conf`, in-memory session cookie, per-IP attempt throttling, `admin.py --set-password`), and `require_secure()` refuses to serve the panel over plain HTTP from anywhere but localhost — a password over plain HTTP is the admin password handed to every Wi-Fi on the way, so until the domain + certbot land it stays on an SSH tunnel. Seven screens: today's attention list, the camera-report queue, live mobile markers, feedback with statuses, health; plus «Люди» — the product funnel from `usage_stats` — and **«Положение»**, the camera-position workflow: a ranked queue of suspicious points (a driver's `wrong_location` complaint outweighs any heuristic; then snap-landed-on-footway, then no road shape at all) leading to `/cameras/<id>/map`, where the camera is dragged on a Yandex satellite map inside a 500 m circle — the same `overrideMaxMoveMeters` the app enforces, so the panel refuses what the phones would reject anyway. The page states the cost of a move on screen: a moved camera loses its measured road profile and starts warning both ways. It is the only page with a script (`static/map.js`, served from a whitelist — never by name from the URL) and the only one with a relaxed CSP, scoped to Yandex's domains. The Yandex key lives in `admin.conf`, never in git. It closes the loop that used to be open: nothing ever wrote `camera_reports.resolved`, and moderation meant a `SELECT` in an ssh session. It **publishes nothing itself** — decisions accumulate in the `overrides` table and the owner signs and ships them with `publish_overrides.sh`, so a compromised VPS can neither hide a camera nor plant one. Hiding is suggested (never applied) at ≥3 `gone` reports from **distinct IPs**, no `still_here` for 14 days, and the oldest report at least a week old; a human confirms with a second click. `test_admin.py` covers it (20 cases), mostly asserting what the panel must *not* do. `radarmap-admin.service` is its systemd unit.
- `snap_cameras.py` / `snap_cameras.sh` — the offline pass that snaps camera coordinates to the OSM road axis **by matching road name** (not just nearest road, to avoid moving a camera onto a parallel street) and derives the per-camera road profile the alert pipeline uses (`axis`, `dir`, `lanes`, `cls`, `road`, `split`, `twin`; a `twin` is kept only when the partner is proven, one-lane roads are not narrowed — `TwinCheck`). It never touches the live DB: outputs land next to it in `server/snap/` (`snap_report.csv`, `snap_moves.geojson`, `snap_dups.csv`) for visual review on geojson.io before you promote them.
- `resnap_moved.py` / `test_resnap_moved.py` — пересъёмка дорожного профиля камер, перенесённых модератором: берёт move-строки из `overrides.json`, выводит профиль заново у новой точки тем же кодом снапа (точку модератора не двигает), переразмечает twin по всей базе; выход — кандидат базы + CSV, дальше обычный `deploy_db.sh` и публикация overrides без влитых move-строк.
- `update_cameras.py` — pulls MVD open-data set 1-008-0027 from data.egov.uz, dedups/normalizes, refuses to proceed on an implausibly small parse, and writes **`cameras_candidate.json`** when the sha changed (idempotent, safe on a schedule). It deliberately does *not* touch the live `cameras.json`/`version.json`: the signing key is not on the VPS, so a compromised server cannot publish cameras. It also watches the MVD accident dataset and shouts into the log if it ever stops being empty. (Its module docstring still describes the older behavior of writing the live file — the code is the authority.)
- `import_poi_egov.py` / `build_camera_candidates.py` / `telegram_publish.py` (13 Oct, each with tests): the open-data portal (data.egov.uz, CC BY-SA 4.0 — credited in Settings → «Источники данных» and `server/ATTRIBUTION.md`) feeds **ATMs of the Central Bank and certified hotels** into the venue files (`server/poi/egov_*.geojsonl`, merged with OSM by `build_roads.py --venues-extra`, 30 m dedup, OSM first); **camera candidates** (OSM `highway=speed_camera` via pyosmium on the local extract + the four regional Statistics-Committee sets, anything > 300 m from the DB → `server/review/camera_candidates.json`, 198 points) are a review queue on the admin «Положение» screen with a «Отклонить» decision table — never applied to the DB; the **Telegram channel** cron posts independently-confirmed radar/tripod/post reports grouped by city, time rounded to 5 min, coordinates to 4 decimals, no device/IP (a test greps), idempotent via `telegram.db`, off until `/opt/radarmap/telegram.conf` exists. Venue kinds are a server↔client contract (`VENUE_KINDS` ↔ `Venue.Kind`): 1 fuel … 10 supermarket, **11 hotel, 12 CNG (метан), 13 LPG (пропан)** — gas by `fuel:cng`/`fuel:lpg` tags or by name («АГНКС», «метан», «пропан»).
- `build_roads.py` / `publish_roads.sh` / `test_build_roads.py` — the signed road set (tiles that fed the now-removed sketch, plus the address/venue files search uses): the OSM geojsonl extract → 210 tiles of 0.5° (`{"version":1,"roads":[[cls, flags, [lat,lon,dlat,dlon,…]]]}` — delta-coded 1e-5°, flags 1=oneway 2=bridge 4=tunnel) plus `index_payload.json` carrying each tile's sha256. `publish_roads.sh` builds on the VPS, signs the **index** locally with the owner's Ed25519 key, ships tiles first and the signed `roads_index.json` last — one signature covers the whole set, and a tile swapped on the server fails its sha on the phone. Client side: `RoadTiles` (format contract, tested against the same numbers as `test_build_roads.py`), `TileRoadNetwork` (0.01° grid, border duplicates collapsed), `RoadNetworkService` (weekly index, lazy 3×3 coverage driven by dashboard ticks, fail closed), `FallbackRoadNetwork` (tiles where covered, limit-index network otherwise).
- `build_limits_index.py` / `publish_limits.sh` / `test_build_limits_index.py` — the signed limits set. `extract_speed_limits.py` (monthly cron, `update_speed_limits.sh`) keeps writing `speed_limits*.json` on the VPS for old builds; `publish_limits.sh`, run by the owner, pulls both files to the mac, gates them locally (v1 must equal v2 minus the class — a pair grabbed mid-cron is refused — plus shape and the cron's own `MIN_SEGMENTS`), copies them under sha-named paths in `limits/`, signs the index with the owner key, uploads files (+`.gz`, atomically) **first**, checks `sha256sum` on the server, then the index **last**, and prunes `limits/` down to the new and the previous set. `status.py` flags a missing index or a signed set lagging the cron as WARN.
- `build_lane_overlay.py` / `publish_lanes.sh` / `lanes_gaps.py` (20.8) — the signed lane overlay (`docs/lanes_overlay_contract.md`, owner's manual `docs/integration_lanes.md`): CSV/GeoJSON/OSM `turn:lanes` → `lanes/lanes.<sha16>.json` + signed `lanes_index.json`; any defect refuses the whole build; `--osm` exists because the OSRM rebuild cron is off since 19.07 (the graph does not fit in memory), so OSM lane edits reach phones only through the overlay. `lanes_gaps.py` ranks junction approaches by aggregated traffic that still lack lanes — the mapping queue.
- `build_hotspots.py` / `publish_hotspots.sh` / `test_build_hotspots.py` — the tripod memory above: aggregation runs on the VPS (the report DB lives there), signing happens on the owner's machine, so a compromised server can neither invent a hotspot nor erase a real one. `publish_hotspots.sh` re-runs the logic self-test, then validates the payload **before** signing — bounds, thresholds, and a grep for `device`/`ip`/`created`, since a signed leak would already be everywhere by the time anyone noticed.
- `sign_db.sh` / `deploy_db.sh` — the OTA release path, run **by the owner from a local machine**: sign the DB with the Ed25519 key (which lives only at `~/.radarmap/ota_signing.pem`, outside the repo — back it up), build `version.json` (version, count, sha256, sig), then `scp` DB + manifest to the webroot. `deploy_db.sh <version>` is the whole publish step, and it ships `RadarMap/Resources/cameras.json` — i.e. the app bundle and prod are published from the same file.
- `nginx-radarmap.conf` (`:8090` → `/api/`, `/osrm/`, static) and `HTTPS.md` (the domain + certbot migration plan).

The VPS also serves the camera DB and speed-limit files (nginx :8090) and runs OSRM in Docker (CH algorithm, `--mmap`) on an Uzbekistan OSM graph. Since the DB must be signed, refreshing it is no longer fully automatic: per `docs/plan_modules.md` the camera cron is off on purpose and the intended regimen is manual and roughly monthly — run `update_cameras.py` → diff the candidate → `deploy_db.sh <version>` → verify the app picks it up. The road graph + speed limits still refresh monthly.
