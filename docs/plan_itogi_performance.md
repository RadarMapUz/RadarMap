# План: перформанс и Итоги 2.0

Составлен 5 августа 2026 по фактическому состоянию кода (203 теста, ветка
`feature/trip-summary-redesign`). Оценки: **дёшево** — до дня, **средне** —
2–4 дня. Порядок внутри части — это и есть приоритет.

Контекст: жалоба «приложение лагает». Ниже — что нашлось чтением горячих путей
рендера. Главный подозреваемый — карта в поездке: контент перерисовывается
каждую секунду GPS, и в перерисовку затянуты все маркеры.

## Часть 1. Перформанс

### 1.1 Карта: 220 маркеров пересобираются на каждый GPS-тик (дёшево, P0)

`MapScreen` — 944 строки, один `body`; внутри `Map { ForEach(map.visibleCameras) }`
(до 220 аннотаций, `AppConfig.maxVisibleAnnotations`). Три причины, почему весь
этот набор перерисовывается ежесекундно во время поездки:

- **`env.speedLimits.limit(near: camera.coordinate)` вызывается для каждого
  маркера при каждой перерисовке** (`MapScreen.swift:272`). Это спатиал-запрос ×
  220 × каждый тик. Лимит камеры не меняется — его надо считать один раз при
  сборке слоя в `CameraMapContent.layer` (он уже выполняется вне main) и хранить
  в элементе слоя рядом с камерой.
- **Каждый маркер читает `env.location.nearestCamera`** (сравнение
  `camera.id != nearestCamera?.id` в `compact:`). Ближайшая камера меняется
  часто → SwiftUI инвалидирует все 220 аннотаций. Ввести `map.highlightedNearestID`
  в `MapState`, обновлять его из `onChange(locationTick)` с дедупом — маркеры
  зависят от значения, которое меняется только при реальной смене камеры.
- **`env.route.traveledPolyline` пересоздаётся каждый тик** → пересборка
  контента карты ежесекундно всю поездку. Обновлять с шагом по накату
  (~25 м), как уже сделано в CarPlay (`AppConfig.carPlayTraveledStepMeters`).

Сюда же: разбить `body` MapScreen на подвью (панели, оверлеи, контент карты),
чтобы инвалидация от тика не проходила через весь экран. Это самая большая
отдача на вложенный час.

### 1.2 Итоги: пересчёт всей истории каждую секунду (дёшево, P0)

`TripStatsSheet.body` считает `TripHistory.summary(trip.history, period:)`
прямо в body. Пока Итоги открыты в активной поездке, liveCard читает
`speedKmh` → body переисполняется каждую секунду → полный проход по истории
(50 записей × проезды) ежесекундно. Перенести в `@State` + `.task(id:)`
(ключ: период + счётчик истории), как уже сделано для `mapData`.

### 1.3 Мерить, а не гадать (дёшево, P1)

- `MetricsService` уже собирает MetricKit — вытащить из payload'ов
  hang rate / scroll hitches и смотреть их после каждого релиза.
- Один прогон Instruments (SwiftUI View Body + Hitches) на девайсе в живой
  поездке — до и после 1.1/1.2, чтобы был факт «стало Х → Y».

### 1.4 Кандидаты второй очереди (P2, только после замеров)

- `glassEffect` на каждой карточке и «стеклянные» панели — дорогие композиции;
  проверить вклад на старых устройствах.
- Каскадные entrance-анимации Итогов и `scrollTransition` строк списка.
- График месяца: 30 `BarMark` + градиент на каждый — дёшево, но проверить.

## Часть 2. Итоги 2.0 — по секциям

Сделано в этой ветке (коммит `ca4f55d`): разбор периода словами
(`PeriodInsights`, 15 тестов), KPI-полоса вместо сетки 2×2, «Когда рискуете»
(часы суток), «Ближайшая цель» в достижениях, дельта рейтинга под кольцом,
жёсткий край прокрутки. Дальше — что докрутить в каждой секции, по пользе:

1. **Деталка поездки: из чего сложился балл** (средне, P1). Самый частый
   вопрос — «почему 68?». `DrivingScore.tripScore` уже считает компоненты
   (штраф за камеры по ступеням, плавность) — вернуть разложение наружу:
   «−25 камера на Юнусабаде (+22 км/ч), −7 резкие разгоны». Хранить в
   `TripRecord` не надо — считается из `passed` + трека на открытии деталки.
2. **Зона риска: топ-камеры с ценой** (дёшево, P1). Сейчас одна сумма за
   период. Добавить под ней до трёх строк: камера · сколько раз · ≈ сумма;
   тап — карта с фокусом на ней. Данные уже в `PassMarker`.
3. **График километров: тап по дню** (дёшево, P1). Столбик выбирает день →
   список поездок подкручивается к этому дню (механика выбора уже есть у
   карты). Сейчас график только смотрит.
4. **Карта: чип «только с превышением»** (дёшево, P2). Слой частоты и маркеры
   есть; фильтр по `hasViolation` — один переключатель над картой.
5. **Достижения: момент получения** (дёшево, P2). Новый earned после поездки
   никак не отмечается — подсветить бейдж и показать строку в разборе
   («Достижение: 1 000 км»).
6. **Список поездок: свайп-экшены** (дёшево, P2). Удаление/повтор сейчас
   только в context menu — добавить трейлинг-свайп.
7. **Шеринг-карточка периода** (средне, P2). Добавить в неё разбор (главный
   вывод) и часы риска — сейчас карта + четыре цифры.

Не делаем сознательно: вкладки внутри Итогов (одна прокрутка честнее),
геймификацию сверх достижений, сравнение с «другими водителями» (нет данных).
